Fixed: a decimal integer literal whose true value lies in (2^63, 2^64-1] is refused with E285 when it is read as a signed integer — a plain i64 position (`print_int(9223372036854775809)`), a signed annotation (`let x: i64 = …`), or an unannotated `let`/`var` binding, which is born i64. As an i64 the literal used to run as the wrapped negative with exit code 0: 9223372036854775809 printed -9223372036854775807. This is the checker's half of ADR-015 row 1 (the band the parse-time width test deliberately leaves).

The refusal is spelling- and type-directed, so every program that was already correct stays correct: the band literal keeps its meaning as a u64 bit pattern under a u64 annotation (the six annotated corpus sites), hex/binary/octal spellings stay type-independent bit patterns everywhere, decimal 2^63 itself keeps its documented wrapped value (tests/run-pass/int_literal_decimal_2_63_print.sio), and `-9223372036854775808` stays the i64 MIN idiom (tests/run-pass/int_literal_min_spelling_still_accepted.sio). lean_single is intentionally untouched: its typechecker maps `u64` annotations onto ty_i64, so there is no unsigned target for the band literal to be adopted by and a refusal there would reject its own supported programs; the shared E276 width refusal still applies to both engines.

Not covered (named on card SIO-428): band literals under arithmetic or comparison operators and implicit function-tail returns still take the i64 wrap; those flow through SIO-207 (runtime overflow) or a later slice of the checker half.
