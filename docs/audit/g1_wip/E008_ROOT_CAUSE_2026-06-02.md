# E008 "expected ()" — root cause + the parity fork (2026-06-02)

The #1 corpus lever (the spurious E008 "return value does not match … expected ()" that the
handoff measured at ~106 programs) is **root-caused, with a working fix** — but the fix alone
**worsens oracle-parity by 82** and must not ship without its companion (effect-validation).
Banked as a patch (`fn_sigs_e008_fix.patch`), NOT committed.

## Root cause — a nested-write-doesn't-persist codegen-pattern bug

Instrumented `--check` on `fn f() -> f64 { return 1.0 }`:

```
collect_fn_def: sig_id=0, count after insert = 0   ← write didn't stick
check fn-item:  fn_sigs.find = -1, count = 0       ← table empty
return check:   current_return_type.kind = 3 (TyUnit)   ← "expected ()"
```

`checker_collect_fn_def_inplace` ran, but `(*c).fn_sigs.entries[i] = sig; (*c).fn_sigs.count = …`
**did not persist**: `(*c).fn_sigs` materialises a *copy* of the 45KB FnSigTable, the nested
write lands on the copy, and it is discarded. So `fn_sigs` stayed **empty**. With no
signatures, `find` returns −1, `current_return_type` never leaves its `ty_unit()` default, and
every `return <expr>` mismatches `()` → spurious E008. (Tail-returning fns escaped because the
body-tail check is guarded by `if sig_id >= 0`, which was false — so they passed *vacuously*,
unchecked.)

This is a **class** bug, not a one-off. The working struct/enum collectors use whole-field
reassignment (`(*c).structs = (*c).structs.add(info)`) and persist correctly. The sibling
`(*c).env.bindings[i] = …; (*c).env.count = …` fn-name binding (check.sio ~2290) has the
identical antipattern and is **also broken** — which is why function names are never bound in
env and the *mut checker cannot resolve identifiers (the 61 unknown-ident leniency below).

## The fix (banked, not shipped)

1. `fn_sigs`: replace the nested write with `(*c).fn_sigs = (*c).fn_sigs.add(sig)` (the 45KB
   copy is fine — it is not the 8MB Checker). → signatures populate, return types resolve.
2. Int↔int return parity: lean_single collapses every integer width to one type code, so it
   accepts any int→int return (the `fn main() -> i32 { …; 0 }` exit-code idiom). Mirror it in
   the body-tail + return-stmt checks (`is_integer_type(a) && is_integer_type(b)`), else
   turning on return checking spuriously rejects every such `main`.

## Why it can't ship alone — the parity math

Measured vs committed baseline (847 examples @1GB), then **oracle-vetted every win** (the sweep
cannot see a false-pass):

| change | 1→0 wins | of which genuine (oracle rc=0) | of which FALSE-PASS (oracle rejects) | net parity |
|---|---|---|---|---|
| E014+E003 (shipped `eb0a26383`) | 13 | 10 | 3 | **+7** |
| fn_sigs + int-int (this patch) | 286 | 99 | 181 | **−82** |

The 181 false-passes are the modular *mut checker's **pre-existing leniency**, unmasked: the
spurious E008 had been *accidentally* rejecting these buggy programs for the wrong reason.
Breakdown (oracle's actual rejection reason):

- **120 effect-not-declared** — `current_effects` is *now populated* by the fn_sigs fix;
  effects are intra-file; the rule is simple ("used effect must be in the signature").
  **Tractable** — this is the companion fix.
- **61 unknown-identifier/method** — genuine (91/102 have no imports; e.g. `dual_var`,
  `beta_new` are undefined in-file, not import confounds). Needs active ident-resolution
  *checking* in the *mut path (a feature; the env-binding nested-write fix is necessary but
  not sufficient — the checker must also error on unbound names).

## The decision (parity-delta rule)

Ship only net-positive-parity changes. So:

- **fn_sigs alone: −82 → DO NOT SHIP.**
- **fn_sigs + int-int + effect-validation: +99 − 61 = +38 → shippable** (the real target).
- **+ ident-resolution: +99 − 0 = +99** (full front-half).

A false-pass is strictly more dangerous than a false-reject for a *self-hosting* type-checker
(a wrongly-accepted bad program is how broken compiler code ships), so the −82 is a hard block,
not a judgement call.

## UPDATE — effect-validation is NOT a quick increment: it re-opens the crash class

User greenlit "go all the way (+99)". Attempted the effect half first by fixing the **third
instance** of the nested-write class bug — the env fn-name binding
(`(*c).env.bindings[i] = …; (*c).env.count = …` → `(*c).env = (*c).env.bind(name, ty_fn(sig_id),
false)`). This was the right fix (function names now resolve), and the call-site effect check
(`checker_check_callee_effects_inplace`, already present at 3707) **does** fire — minimal
`fn g() with Mut {} fn f(){ g() }` now correctly reports the effect error (rc=1, no crash).

BUT the full sweep regressed catastrophically: **364 crashes** (350 `1→139`, 14 `0→139`). Root
cause: binding fn names turns callees from `unknown` (the lenient branch 3710, which skips all
arg work) to `TyFn` (the real branch 3703 → `checker_check_call_args_inplace` +
`release_call_arg_borrows`). **That arg-checking path was hand-written in the 481→0 crash arc
but NEVER ACTUALLY EXERCISED** — because callees never resolved, the arg-checker's `*mut`-safety
was untested. Trigger is precise: a call **with arguments** crashes (`g(5)` → 139 at both 1GB
and unlimited stack = SRET-smash, stack-independent); a no-arg call (`g()`) does not. So a
by-value Checker SRET survives somewhere in the now-live arg-check / call-resolution sub-tree
(candidates: `call_arg_types_compatible`, `fn_sigs.get`, the `(*c).borrows` copy held across
the arg recursion, or a boundary-contract sub-path) — locating it needs gdb on a crashing
corpus program (e.g. `ablation_suite`, `algebra_demo`).

**Revised scope:** effect-validation (and therefore the +38/+99 path) is gated on a fresh
**crash-elimination sub-arc** over the now-live arg-checker — the same SRET-class `*mut`
migration as 481→0, applied to the call-resolution sub-tree. It is NOT the one-increment +38 I
estimated. The env-fix attempt (fn_sigs + int-int + env) is banked as
`fn_sigs_e008_env_fix.patch` + `mc_T_env_experiment.elf` for a gdb-equipped resume.

## gdb + marker-trace of the 364 crashes (the arg-checker SRET)

Diagnosed the `g(5)` minimal repro (call-with-args, the precise trigger) on the env-fix binary:

- **gdb**: faults at `mov 0x0(%rdx),%rax` with **`rdx = 0xFFFFFFFFFFFFFFFF` (−1)** — dereferencing
  a −1 sentinel. The instruction copies a 272-byte (34-qword) struct field-by-field into a
  **168KB-deep frame local** inside a **168KB-frame function** (= `checker_check_call_args_inner_inplace`,
  the arg-checker — large frame from marshalling the boundary-contract args). `rbp−rsp = 672KB`
  (not a 12MB recursion frame); crashes identically at 1GB and unlimited stack ⇒ **not** stack
  overflow — a corrupted-pointer struct copy.
- **marker-trace**: the 5 per-arg boundary contracts run in order borrow→refinement→knowledge→
  unit→ontology. Markers show borrow/refinement/knowledge pass; **unit_boundary enters and runs
  its whole body** (it's a no-op for an `i64` arg), then `print` *after* the unit call in the
  caller never fires — the fault is in unit_boundary's **return/epilogue back into the
  168KB-frame caller**. Adding markers **moved** the apparent crash point (ontology-area →
  unit-area): it is **layout-sensitive**.

**Conclusion:** this is the bin/souc **large-by-value-`TypeEntry`-arg codegen miscompile** — the
same SRET-class/layout-sensitive bug family the whole 481→0 arc fought — surfacing because the
boundary contracts (`arg_ty: TypeEntry, param_ty: TypeEntry, call_span` by value) are now
*actually exercised*. It is NOT a single-function logic bug. The likely real fix is to pass the
boundary-contract args **by pointer** (`*const`/`*mut`) instead of by value, across the 5
contracts + `checker_check_call_args_inner_inplace` — a contained but multi-function sub-arc.

One concrete latent SRET WAS found and fixed along the way: `checker_ontology_boundary_check_call_arg_contract_inplace`
returned the 8MB Checker by value (SRET); transcribed it to a true `*mut` void call (queries via
the free `ontology_kernel_is_*` fns, report via `*mut`). Correct, but inert for `g(5)` because the
unit-area miscompile faults first — banked in `fn_sigs_e008_env_ontology.patch`, unverified by
execution.

## The by-pointer sub-arc — attempted in full, does NOT fix the crash

Converted all 5 per-arg boundary contracts + their call sites to take `arg_ty`/`param_ty`/
`arg_expr` **by reference** (`&T`, deref at top) — verified Sounio supports `&local`/`&field`
read-refs (`reftest` rc=7, two-`&`-args rc=1). Built clean. **g(5) still crashes** — and the
crash *changed form*: from `mov 0x0(%rdx),%rax` with `rdx=−1` (bad struct deref) to **`rip = 0x0`**
(RET to null = **return-address smash**), still a ~675KB frame, still identical at 1GB and
unlimited. So the by-ref args were not the cause; the smasher is a large-struct **value-RETURN**
(SRET) in the arg path corrupting the return address.

**The smasher is a `TypeEntry`-sized (272B) value-op, layout-sensitive — a bin/souc codegen bug,
not source-fixable here:**
- The gdb fault copied a **272-byte (34-qword) = `TypeEntry`** struct — and `checker_check_expr_inplace`
  / `call_ref_inner_or_self` / `fn_param_list_get` all return `TypeEntry`-bearing structs by value.
  `checker_check_expr_inplace` returns `TypeEntry` (272B) successfully **everywhere else in the
  spine** — so this is not a size threshold; the *same* op smashes only in the arg-checker's
  specific frame layout. That is the documented SPAN/whitespace-sensitive bin/souc codegen bug.
- The clean source workaround (eliminate the SRET via a write-back out-param) is **blocked by a
  Sounio limitation**: `&! structLocal` does **not** write back (`outp3`/`outp4` both return 0,
  not 14 — field-store and whole-struct store alike). Only heap `*mut T` (`heap_alloc as *mut T`)
  mutates through a pointer; you cannot take a working `&mut` of a stack struct. So `fn_param_list_get`
  (and the other `TypeEntry`-returning utilities) cannot be cheaply de-SRET'd in place.

**Conclusion:** clearing the arg-checker crash is NOT a contained source sub-arc. It needs either
(a) a **bin/souc codegen fix** for the layout-sensitive large-struct value-op miscompile
(bootstrap-level — the real root), or (b) heap-allocating the arg-path's `TypeEntry`/`FnParamInfo`
temporaries so all of it goes through `*mut` (a pervasive, invasive refactor of shared utilities).
Both are out of scope for the verdict-parity arc. The by-ref attempt is banked as
`fn_sigs_e008_env_ontology_byref.patch` (built clean, faithful, but moves rather than fixes the crash).

## Codegen-fix attempt — STOPPED at confirmation: it is NOT frame overflow

Before touching `lean_single` codegen + re-bootstrapping (the riskiest op in the repo), did the
read-only confirmation (advisor-directed). The hypothesis was an SRET stack-slot leak overflowing
the frame (`emit_sret_destination_x86` does `NEXT_SLOT += ret_slots`, `local_bss_spill_bytes()`
=512KB so a 272B TypeEntry SRET uses stack slots). **The disassembly refutes it:**

- Crashing function prologue: `push %rbp; sub $0xa48c0,%rsp` (~658KB frame). The prologue stores
  the register args: `rdi→-0x8, rsi→-0x10, rdx→-0x18, rcx→-0x20`. So **slot `-0x20` is an
  ARGUMENT slot**, 32 bytes below rbp — comfortably *within* the 658KB frame (which is under the
  4MB cap). It is **not** a slot counter walking off the end.
- The crash loads slot `-0x20` (value `-1`) and does `mov 0x0(%rdx)` — dereferencing `-1` as a
  272-byte struct pointer.

**Discriminator (advisor): garbage rbp-relative address = frame overflow; exact sentinel = bad
value. `-1`/`0` are exact sentinels** (uninitialized slot, None-encoded `Option<Box>`, or a
zeroed/partial struct write) → **bad value, NOT SRET frame overflow.** So the SRET-codegen-fix +
re-bootstrap would have fixed the wrong mechanism. The mc_T (rdx=-1) and mc_V (rip=0) crash
points also differ by build → layout-sensitive, so a single exact slot is not fully reliable;
the *class* (sentinel-as-pointer) is the robust finding.

**Most promising lead for a fresh session (cheap, source-level, no bootstrap):** the `-1` is a
mishandled None / corrupted `Option<Box>` dereferenced as a pointer. Prime suspect = `sig.params`
(`Option<Box<FnParamList>>`) read back **corrupt after the `(*c).fn_sigs = (*c).fn_sigs.add(sig)`
round-trip** (a by-value FnSig copy carrying a nested `Option<Box>`), then `fn_param_list_get`
deref's it. Confirm by instrumenting `check_call_expr` to print `sig.param_count` /
`is_none(sig.params)` for a resolved call — if the Box is corrupt, this is a struct-copy /
`Box::new`-of-nested-`Option<Box>` bug (possibly source-fixable), NOT the SRET path. Do this
BEFORE any `lean_single` edit. If re-bootstrapping is ever needed: build gen1/2/3 as scratch,
**never overwrite `bin/souc*` until gen3 + full `tests/run-pass/*` + the 847-corpus + canonical
gate pass** (gen2==gen3 proves self-consistency, not correctness).

## sig.params lead — REFUTED (cheap source-level test, no bootstrap)

Instrumented the resolved-call site (`mc_sp.elf`, env+ontology) to print `sig.param_count` +
`sig.params` shape right after `(*c).fn_sigs.get`. For `g(5)`:

```
sig.param_count = 1                       (correct — g has 1 param)
sig.params = Some                          (not None)
(*pbox).head.ty.kind = 0 (TyI64)           (Box is VALID, points to the real `x: i64` param)
[then crash]
```

So **`sig.params` is valid going into the arg-checker** — the `fn_sigs.add`/`get` round-trip
preserves the nested `Option<Box>` correctly. The `-1` is **not** corrupt sig.params; it arises
*inside* the arg-checking path. **Both hypotheses are now refuted by direct evidence: not SRET
frame-overflow, not sig.params corruption.**

### Where that leaves the codegen fix

The crash is a **layout-sensitive `-1`/`0` sentinel dereferenced as a pointer** in the
arg-checking path (`checker_check_call_args_inner_inplace` / the per-arg boundary calls), and the
exact faulting slot/function **shifts across builds** (mc_T rdx=−1 vs mc_V rip=0) — so cross-build
gdb forensics can't pin the single source. Diagnosing it further needs a **build-independent
reproducer** (a small standalone `.sio` that `bin/souc` miscompiles the same way — *not yet
found*; the bug may need the `*mut Checker` 8MB-struct context) + systematic per-call instrumentation
on ONE binary, then matching the bad instruction to the `lean_single` codegen path that emits it.
That is a fresh, focused session — and the codegen edit + re-bootstrap (build gen1/2/3 as scratch,
never overwrite `bin/souc*` until gen3 + full `tests/run-pass/*` + 847-corpus + canonical gate
pass) is the step after the mechanism is actually nailed, not before.

**Net of the codegen-fix attempt:** two confident *negative* results (ruled out SRET-overflow and
sig.params), which is real progress — it stops a risky re-bootstrap aimed at the wrong mechanism.
No codegen change made; branch stays at +7.

## Build-independent reproducer hunt — NOT FOUND (bug is emergent at full-compiler scale)

Tried to produce a small standalone `.sio` that `bin/souc` miscompiles the same way (for a fast
codegen-fix iteration loop instead of the 156s mc.elf rebuild). Candidates, all with an 8MB
`*mut Huge` context + 272-byte `TE` structs (mirroring `*mut Checker` + `TypeEntry`):
- structural mimics (SRET helpers held across calls, `Option<Box>` param lookup),
- frame growth (30 → 1800 struct locals, up to ~478KB frame),
- deep recursion passing structs by value + nested struct-returning helpers,
- 400 functions each passing structs by value.

**All compile and run CORRECTLY — none crash (rc≠139) and none miscompute.** So the arg-checker
crash does NOT reproduce in a standalone program; it is emergent at full-`mc.elf` scale —
consistent with the documented [[project_modular_span_sensitive_crash]] whitespace-sensitivity
(the crash depends on the full binary's exact byte layout / function addresses, not a local
structural pattern).

**⚠️ Methodology retraction:** an intermediate run appeared to show an "8-bit truncation
miscompile" (struct local `vN` reading as `v(N mod 256)`). That was a **measurement error** — I
was reading the program's **process exit code**, which Linux truncates to 8 bits (`return 300`
→ shell sees `300 & 0xFF = 44`; `1000 → 232`; `256 → 0`). Re-verified with `print()`: `v600` →
**600**, literal `1000` → **1000** — the programs are correct. No 8-bit codegen bug exists.
Lesson: **never read a value > 255 via exit code; use `print()`.** (Crash detection via rc=139 is
still valid — a signal, not a truncated value.)

**Consequence for the codegen fix:** there is no fast standalone reproducer, so the fix cannot be
iterated on a small program — it must use the full `mc.elf` build loop (edit `lean_single` → build
gen1 [156s] → gen1 compiles main.sio → mc.elf [156s] → test `g(5)`), ~5 min/iteration, on a
layout-sensitive bug. That makes the codegen fix a slow, high-care effort — and reinforces that
the mechanism must be nailed by instrumentation on the real mc.elf path first, not guessed.

## On-real-path instrumentation — the −1 origin RELOCATES with every source change (definitive)

Instrumented the per-arg boundary block on the real mc.elf (env+ontology), printing
`arg_ty.kind`/`param_info.ty.kind` after each of the 5 boundary calls for `g(5)`:

```
600000000 → arg=0 param=0   (before borrow)
600000001 → arg=0 param=0   (after borrow)
600000002 → arg=0 param=0   (after refinement)
600000003 → arg=0 param=0   (after knowledge)   ← data still VALID here
[crash — 600000004 never prints]
```

So the data (arg_ty, param_ty) is **valid right up to the unit-boundary call** — not corrupted.
The crash is the unit call itself. unit_boundary held `let t = (*c).report_unit_call_mismatch(…)`
— a **by-value Checker (8MB) SRET** local (forcing an 8MB frame even when the error branch is
not taken), the twin of the ontology SRET already fixed. Fixed all three call-path Checker-SRET
locals to `*mut` (`report_unit_call_mismatch` / `report_effect_error` /
`report_hypothesis_penalty_warning`; banked `fn_sigs_e008_env_ontology_reports.patch`).

**Result: still crashes — and the crash MOVED.** With the 8MB frames gone, gdb on the rebuilt
binary shows `rip=0` (return-address smash) in a **2KB-frame** function (vs the prior 658KB
frame), and the boundary markers no longer print (crash now *before* the boundary block). So the
report-SRET fixes were correct (removed three 8MB frames) but did **not** fix the crash — it
relocated to whatever function's layout trips next.

**This is the third independent confirmation that the crash relocates with any `check.sio`
change:** (1) by-ref boundary args moved `rdx=−1` → `rip=0`; (2) the report-SRET fixes moved the
crash from the unit boundary to before the boundary block, into a small-frame function. **The −1
origin is therefore NOT a stable source location** — it is a layout-sensitive return-address-smash
in bin/souc's codegen that re-homes to a different function after each edit. It cannot be pinned
or fixed at the `check.sio` source level; source instrumentation chases a moving target.

**Conclusion (firmer):** the fix must be in bin/souc's codegen — pin the *exact* smashing
instruction in a FIXED binary via gdb (what writes 0/−1 onto `[rbp+8]` = the return-address slot),
match it to the `lean_single` emit path (struct-copy / SRET-dest / call-arg marshalling), fix
that, and re-bootstrap with FULL `tests/run-pass/*` validation (a swap that skips this is exactly
how the `Epistemic::measured` `val=0` regression got into `/workspace/sounio`). The moving-target
nature means a source-side fix is not possible; this is a codegen-only, fresh-session effort.

## Status

Five patches banked (`fn_sigs_e008_fix.patch` = fn_sigs+int-int; `fn_sigs_e008_env_fix.patch` =
+env; `fn_sigs_e008_env_ontology.patch` = +env+ontology-SRET-fix) + their experiment binaries. The committed branch stays at the +7
`eb0a26383` (E014+E003) baseline — the only net-positive, crash-free shippable state this
session. The full E008 resolution is: (1) fn_sigs whole-field fix [done in patch], (2) env
whole-field fix [done in patch], (3) **gdb the arg-checker SRET-smash and `*mut`-migrate the
now-live call-resolution sub-tree** [the new sub-arc], (4) int-int return parity [done in
patch], (5) ident-resolution error on unresolved callees [the 61, separate]. Steps 1/2/4 are
correct but inert/harmful until step 3 clears the 364 crashes.
