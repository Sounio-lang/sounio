# The PR mergeability queue is a flow, not a stock — automating the refresh

**Date:** 2026-08-18
**Status:** operational finding + a script. Follow-up to
[`docs/audit/GITHUB_MERGEABILITY_CACHE_STALENESS_CENSUS_2026-08-18.md`](GITHUB_MERGEABILITY_CACHE_STALENESS_CENSUS_2026-08-18.md)
(PR #1838), which treated the phantom/real split as a one-time triage. It was not one-time.

## The finding that changes the previous dispatch's framing

The original census ran once: 54 PRs, 20 phantom (API said `CONFLICTING`, locally clean), 18 real
conflicts. A second census, run later the same day against a fresh 37-PR snapshot of the same
queue, found 18 phantom and **19** real conflicts. Diffing the two real-conflict lists:

- **15 of the 19** were already in the first census's 18 (3 of the original 18 — #978, #1053,
  #1063 — closed without merging in between, read as abandonment per the first dispatch, not
  resolution)
- **4 are new**: #1790, #1831, #1841, #1842 — none of these existed as conflicts in the first
  census because their branches (or `main`'s state) hadn't diverged yet.

That is the finding: real conflicts are not a fixed backlog waiting to be cleared. They are a
**continuous flow**, generated by `main`'s own advance at the rate this repo runs it (dozens of
commits/hour). A census that runs once measures an instant of that flow and goes stale within the
hour, exactly the way the phantom side of the queue does (see the original dispatch's "not durable
against `main` churn" section). Treating this as one-time triage was the wrong model. The
remediation half of the original dispatch already had a repeatable procedure; the analysis half
did not yet call it a flow. This dispatch names that and ships the automation.

## What `scripts/dev/pr_mergeability_refresh.sh` does

Same three rules the original dispatch established by hand, now encoded so they cannot be skipped
under time pressure:

1. **Phantom vs real is decided by local verification, never by the API.** The script runs `git
   merge-tree --write-tree <base> <head>` (git ≥2.38 — the same merge machinery `git merge` itself
   uses) for every PR and branches all subsequent behaviour on that result. `mergeable` /
   `mergeStateStatus` are fetched and recorded **only** to print how often the API disagreed with
   reality — they never appear in a condition that decides whether the script touches a branch.
   This is not a stylistic preference: across the two censuses the API was wrong 6 of 7 measured
   symptom shapes, and 38/91 (42%) of PRs the API called non-mergeable across both runs turned out
   to be clean.
2. **Coordination before pushing to a branch this agent doesn't own.** Before refreshing a
   phantom, the script checks `bin/sounio-coord status` for an `ACTIVE` claim on that exact branch
   and, if found, sends a `bin/sounio-coord send --kind info` heads-up to the owning lane before
   pushing. This mirrors the exact sequence used by hand today against PR #1853
   (`lane/grok-cli3/portfolio-139-untag-20260818`) — claim found, warning sent, push landed clean,
   no collision.
3. **Report the phantom:real ratio every run, not just the counts.** The ratio is the signal for
   whether this script is still earning its keep: high means the API cache is still the dominant
   failure mode in the queue and refreshing is worth the cost; falling toward zero or negative
   (more real conflicts than phantoms) means the queue has shifted toward genuine unresolved
   divergence, and the correct response at that point is finding authors, not running this script
   again. The script prints this number unconditionally — it does not get to declare success by
   omitting a bad ratio.

Real conflicts are never touched, even when `git merge-tree --write-tree` reports clean but the
subsequent real `git merge --no-edit` inside the disposable worktree disagrees (this happened zero
times across 38 refreshes today, but the script treats it as the authoritative stop condition
rather than trusting the cheaper probe once a live merge contradicts it).

```bash
bash scripts/dev/pr_mergeability_refresh.sh                 # all open PRs
bash scripts/dev/pr_mergeability_refresh.sh 1420 1451 1466   # specific PRs
```

Smoke-tested against two known PRs from today's manual census (`1420`: phantom already refreshed
by hand, correctly classified `API-correct`/no-op; `1729`: confirmed real conflict, correctly
skipped and reported, not touched).

## Known real conflict worth flagging by hand, not by script

**#1831 is the Box\<T\> fix — the first positive result on that defect after five prior causes
were refuted.** It is a genuine local conflict (`self-hosted/ir/lower.sio`, confirmed both by
`git merge-tree --write-tree` and a real `git merge --no-commit --no-ff`), owned by `codex-1`.
This is exactly the kind of PR rule 3 exists to protect: script automation would either skip it
correctly (as it did here) or, if rule 1 were ever weakened to trust the API, risk forcing a head
refresh that would only relocate the conflict from the API boundary into the branch itself.
`codex-1` was notified over the coordination bus and via a PR comment naming the conflicting file;
nothing here was touched by this dispatch or by the script.

## What this does not change

The original dispatch's finding about *why* the API cache drifts (main's push rate plausibly
outrunning GitHub's recomputation queue) is unchanged and still unconfirmed from outside GitHub's
infrastructure. This dispatch only changes the operational model from "run the fix once" to "run
the fix on a cadence, and let the printed ratio say when to stop trusting automation and go look
for authors instead."

## Appendix: how long does a real conflict live before its author resolves it

The refresh side of this problem (phantom PRs) has a measured fix with a real, if imperfect,
duration (10–60s to clear, ~15–25min before the API cache can drift back). The other side of the
queue — the 19 real conflicts — was never timed. This appendix does that, using the 19 as the
sample, re-checked fresh against `main`@`d3ea284caf` (2026-08-18, evening).

**Result: 0 of 19 have resolved.** Every one of the 19 still shows `git merge-tree --write-tree`
conflict against current `main`. This includes the 15 that carried over from the first census and
were notified by name, with the exact conflicting file(s), via a PR comment at **09:27 UTC** — over
**6.5 hours** before this re-check, with zero follow-up commits on any of the 15 in that window.

Because zero resolution events occurred, there is no meaningful way to compute a median
*time-to-resolve* from direct observation — the data is right-censored with an empty event set.
What can be measured instead is how long each conflict has already survived unattended, using time
since the branch's last commit as the floor (the conflict cannot have been fixed more recently than
the last time a human touched the branch):

| Metric (days since last commit on the branch) | Value |
|---|---:|
| Minimum (PR #1841, created and last touched the same morning) | 0.01 |
| Median | **21.05** |
| Mean | 17.93 |
| Maximum (PR #795) | 37.03 |

Eleven of the 19 have not been touched in more than two weeks; five have not been touched in over a
month. Only four (#1790, #1831, #1841, #1842 — all under 1 day old) are recent enough that "not yet
resolved" could plausibly mean "not yet noticed" rather than "abandoned." One (#1580) shows a
last-commit 0.26 days ago (shared-worktree churn already noted in the base census) but the touch did
not address the conflicting files — still conflicting on the same 3 files it had at the first
census, so recent activity on a branch is not itself evidence of engagement with its conflict.

**Answer to the question this appendix was written to settle:** the flow does not drain itself. A
short median would have meant the phantom-refresh automation was sufficient — real conflicts would
clear on their own timescale and the only thing worth automating was clearing the API cache noise
around them. A median above three weeks, with a 0/19 resolution rate even 6.5 hours after being
personally notified with the exact file names, means most of this queue's real-conflict PRs do not
have an actively engaged owner right now. That is a staffing/triage problem, not a tooling one —
`scripts/dev/pr_mergeability_refresh.sh` (this dispatch, above) correctly refuses to touch any of
these 19, and it should keep refusing; the fix for this half of the queue is finding or reassigning
owners, not writing another script.
