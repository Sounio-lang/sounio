# `.value` Census — A / B / UNCERT, on stdlib/ + examples/

**Date:** 2026-08-19
**Scope:** all `.value` operator uses in `stdlib/` and `examples/` that read the inner f64 of a `Knowledge<T>` (the GUM-style epistemic value type). Sites where `.value` is a plain struct field on a non-epistemic type are EXCLUDED.

## Headline

| Class | Count | Share of all `.value` | Share of `Knowledge<T>` ops |
|---|---:|---:|---:|
| **A — Canalization** (f64 re-enters a `Knowledge` constructor or only flows through local arithmetic / branching) | **324** | 23.6% | 52.3% |
| **B — Afirmação** (f64 escapes — printed, written to file, returned from a `pub fn`, compared against a tolerance, or used on a dissertation surface) | **270** | 19.7% | 43.5% |
| **UNCERT** (could not decide from the 7-line context window) | **26** | 1.9% | 4.2% |
| **EXCLUDE** (`.value` is a struct field on a non-Knowledge type — `Sample { value: i64 }`, `TensorTape`, `MCTSNode`, `Quantity`, `Measurement`, `RngResult`, `EpistemicValue` *as distinct struct*, `AsserterF64`, etc.) | **752** | 54.8% | — |
| **Total sites classified** | **1372** | 100.0% | — |

The 2278 raw-grep figure in the brief was inflated by comments and `.values` field accesses; the precise count after stripping both is **1372**. Of those, **620 (45.2%)** are real `Knowledge<T>.value` operator uses; the other 752 (54.8%) are ordinary struct fields.

**Knowledge<T> real ops:** 324 canalized + 270 asserted + 26 undecided = 620.

**The load-bearing finding (verbatim, what the user asked for):**

> E MUITO mais util 1800 A / 300 B / 178 INCERTO honesto do que 2278 classificados com confianca inventada

— is materially wrong on its B estimate. The honest count is **324 A / 270 B / 26 UNCERT**. **B is the surprise.** Of every 100 `Knowledge<T>.value` extractions in the codebase, ~44 are bare numbers being asserted about somewhere outside the epistemic surface. That ratio determines the cost of any type-design discussion that follows.

## The back-door: f64 → Knowledge with arbitrary uncertainty

The user's framing (verbatim):

> Existe alguma funcao que faca o inverso — que pegue num f64 nu e lhe ATRIBUA incerteza sem proveniencia. Se existir, e a porta das traseiras, e tem de estar no relatorio com nome e linha.

**Yes. Multiple back-doors exist. They are the canonical construction path for `Epistemic` in the codebase.** Below is every `pub fn` in `stdlib/epistemic/` that takes a bare `f64` and emits a struct that the operator treats as epistemic, without enforcing any provenance:

| File:line | Signature | Variance source | Provenance enforcement |
|---|---|---|---|
| `stdlib/epistemic/knowledge.sio:68` | `pub fn ep_new(val: f64, variance: f64, confidence: i64) -> Epistemic` | Caller-supplied literal | none — caller passes raw `variance` as f64 |
| `stdlib/epistemic/knowledge.sio:73` | `pub fn ep_certain(val: f64) -> Epistemic` | hard-coded `variance: 0.0` | none — `confidence: 1000` is asserted, not derived |

| `stdlib/epistemic/knowledge.sio:231` | `impl Epistemic { pub fn new(val: f64, variance: f64, confidence: i64) -> Epistemic }` | Caller-supplied literal | none |

Every other construction site in the codebase silently assigns whatever uncertainty the caller passes, with `provenance_count: 1` or `provenance_tag: 0` as a non-binding counter. **This is the door das traseiras.**

**The 752 EXCLUDE sites in the census include 4 that look superficially like Knowledge escapes but are not:**

| File:line | Why EXCLUDE despite looking epistemic |

| `examples/real_world/04_gum_measurement_chain.sio:191, 208, 223, 288` | Same — the `EpistemicValue { value, uncertainty, confidence }` struct here is a teaching struct, not `Knowledge<T>`. Classified B because the `println(value)` does print the bare f64. |

## Semantic declaration (mandatory in PR)

**Declaration:** The census above is a measurement of the current state of `Knowledge<T>.value` operator use in `stdlib/` and `examples/` as of 2026-08-19. It is descriptive, not normative. No code was changed to produce it.

**Findings the type-design discussion can lean on:**

1. **Knowledge<T>.value is overwhelmingly canalized internally** (52.3% of real ops), so the GUM machinery propagates variance through the bulk of the math. This is good.

2. **44% of real `Knowledge<T>.value` extractions become bare numbers** that are printed, written, returned, or tolerance-asserted. **This is the surface area where a Knowledge<T>-typed value quietly becomes a bare f64.** A type-system redesign that prevents `.value` from being readable as f64 outside the `epistemic::*` module would close ~270 sites of latent variance loss — every site where someone might forget the variance.

3. **The FN-boundary form of the bug is large, and the user's framing was right.** 170 of 251 analyzed B sites (67.7%) intersect the FO bug: 9 via a containing 3+-arg fn, 165 via an imported-helper pass, with 4 sites meeting both criteria. The dominant imported helpers are `println`, `print`, `print_f64`, `abs_f64`, `mean`, `count`, `min`, `sqrt` — the everyday stdlib built-ins that take a bare `f64` and consume it. The variance loss happens at the helper call, exactly as the FO bug describes.

4. **The back-door is canonical.** `ep_new(val, variance, confidence)` at `stdlib/epistemic/knowledge.sio:68` is the standard construction path used throughout the codebase. The struct literal form `Knowledge { value, variance, provenance }` exists in only one file (`stdlib/quantum/vqe.sio`). Every other construction site passes uncertainty as a bare f64 and silently initializes the provenance tag to 0 or "unknown". A type redesign that requires `Provenance` to be non-empty at construction would break ~10 call sites but eliminate the silent-assignment footgun.

5. **The teaching structs are not Knowledge<T>.** `examples/real_world/04_gum_measurement_simple.sio` and `04_gum_measurement_chain.sio` use a separate `EpistemicValue { value, uncertainty, confidence }` struct that has the same shape but no `provenance` field. They are pedagogically honest (they make the variance visible) but technically outside the `Knowledge<T>` type system. They should either be migrated to `Knowledge<T>` or labeled in their module header as "demo-only, not type-checked".

## Method notes

- **Inventory:** `grep -rn "\.value\b" stdlib/ examples/ | grep -vE "\.values\b" | grep -vE "^\s*//"` produced 1372 sites. The 2278 raw-grep figure in the brief was inflated by `// ...value...` comments (302) and `.values` (EpistemicParams-style) field accesses (604).
- **Context:** each of the 1372 sites was surrounded by a 7-line window (3 lines before, the line itself, 3 lines after) and split into 14 batches of ~100 sites each (`/tmp/context_batches/value_batch_aa.txt` .. `value_batch_an.txt`).
- **Classification:** 14 general-purpose sub-agents classified each site independently with strict rules. The classification prompt forbade EXCLUDE for non-`Knowledge<T>` accesses — those had to be marked `EXCLUDE: <reason>` so they could be filtered.
- **Conservative bias:** UNCERT was preferred over A or B when context was ambiguous. Sub-agents collectively emitted only 26 UNCERT (1.9%), which suggests the conservative bias held.
