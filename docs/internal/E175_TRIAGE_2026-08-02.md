# E175 triage on main.sio — 3 360 errors, 202 declarations, zero violations

**Measured:** 2026-08-02, `souc check self-hosted/compiler/main.sio`, after
`0288f25d8` (an imported name no longer shadows the type it names). That fix is
what made these visible: types that were `TyUnknown` were also unchecked, so
visibility enforcement had nothing to enforce against.

**No `pub` has been added on the strength of this document.** It exists so that
decision is made from the shape of the data rather than from the size of the
number.

## The number is call sites, not work

| | |
|---|---|
| errors | 3 360 |
| **distinct callee declarations** | **202** |
| modules holding them | 26 |
| top 4 declarations | 2 895 errors (86 %) |
| top 1 declaration | 999 errors (29 %) |

The 999 is not a repeat and not a cap: 999 **distinct** caller functions at 999
**distinct** spans, against ~1 016 call sites of `const_prop::cp_empty_instrs`
in the tree. The fix for 86 % of the errors is four annotations.

## Who is calling

**3 090 of 3 360 (92 %) come from callers whose name contains `_test_`** — the
in-tree test suite that lives in `main.sio`, calling module-private helpers.
The two biggest callees say what they are in their own names:

    999  const_prop::cp_empty_instrs      test scaffolding
    999  const_prop::cp_make_test_func    test scaffolding
    690  opt_cleanup::opt_cleanup_function
    207  opt_cleanup::ocp_const_fold

**270 (8 %) come from production code**, across 130 declarations, and they are
intra-subsystem calls that happen to cross a file boundary:

    lower::wasm_lower_binop        -> encode::wasm_body_emit_local_get, …
    server::ipc_serve              -> protocol::ipc_write_result_single, …
    kernel::handle_kernel_execute  -> protocol::ipc_write_error, …

A WASM lowerer calling the WASM encoder is the architecture, not a breach of it.

## Not one of them is an encapsulation violation

Every one of the 3 360 has a **different** caller and callee module id, so none
is the same-module false positive documented in
`tests/compiler/madaros_visibility_context`. And every one is an in-tree,
same-crate call: no consumer outside this repository reaches any of them.

So the question is not "should these be public" — none of them should. It is
"what does this language call a symbol that is internal to the crate but shared
between its modules", and the answer already exists.

## `pub(crate)`, not `pub`

The parser supports it (`parser/items.sio:1172`, `VISIBILITY_PUB_CRATE` in
`parser/ast.sio:967`) and the checker honours it
(`checker_fn_sig_visible_inplace`). **It is used four times in the entire tree.**

`pub` on 202 internal helpers would put test scaffolding like `cp_make_test_func`
into the language's public surface to satisfy a test harness. `pub(crate)` says
exactly what is true: in-tree, shared across modules, not API.

## Recommended order

1. **4 declarations** — `const_prop::cp_empty_instrs`, `cp_make_test_func`,
   `opt_cleanup::opt_cleanup_function`, `ocp_const_fold` → 86 % of the errors,
   and all four are called only by tests.
2. **68 more test-only callees** → the remaining test traffic.
3. **130 production callees** — these deserve reading, not a sweep. Some may
   indicate a module boundary drawn in the wrong place rather than a missing
   annotation, and 130 declarations is small enough to look at.

Step 3 is where a sweep would be wrong, which is the reason this document
exists: 86 % of the number is four lines, and the interesting 8 % would have
been buried under a `sed`.
