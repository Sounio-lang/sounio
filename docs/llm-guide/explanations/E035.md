**E035 — Effect not declared in function signature**

**Baseline context:** source inspected at
`f5b2c5850be9f3d3995719ffcade44a6d851658a`, October 2026 edition. The July
2026 observation that default `check` did not report E035 is superseded as
general guidance. Current modular source contains effect checking and E035
reporters. The separately recorded [bounded conformance receipt](../../spec/2026-10/15-bounded-conformance-receipt.md)
includes an effects-negative case on its identified committed Linux prebuilt.
That receipt is not a fresh source build or proof of every trigger on every
engine. This page introduces no executed examples.

## Cause and route

A checked function body or call requires an effect absent from the enclosing
function's permitted effect row. In modular
[check.sio](../../../self-hosted/check/check.sio), inspect
`report_effect_error_from`, `check_callee_effects`, and the operation that
introduced the effect. The reporter can name the enclosing module/function,
the `missing:` effects, and the `required by` callee. Preserve that context.

The [seed](../../../self-hosted/compiler/lean_single.sio) also has E035
reporters on its own path. Its coverage is a separate question. The MCP
resource's static title “Recursive type rejected” is inconsistent with the
inspected E035 effect reporter; a retrieved title must not override a fresh
message. See [route and identity guidance](../error-catalog.md).

## Repair

1. Compare the called function's actual effect row with the caller's row and
   the task's permitted effects. Inspect a closure/function parameter's
   inferred effects where relevant.
2. Add only the missing, justified effect at the correct boundary, or move
   the operation to an effectful boundary if that preserves the requirement.
   Recheck affected named callers. A blanket list of effects can exceed this
   implementation's signature capacity and can conceal an API change.
3. Recheck on the same identified profile, then verify the required behavior
   or refusal witness. A declaration does not implement an operation or
   establish scientific correctness.

## Operation-specific distinctions

| Source operation | What the inspected route establishes |
| --- | --- |
| Calling a function that declares effects | The callee's required effects participate in call checking; use its real signature rather than a guessed trigger table. |
| Store rooted in an exclusive reference | `checker_check_assign_stmt_inplace` uses `checker_place_excl_ref_root` to introduce `Mut` for supported roots, including relevant dereference, field, and array-index writes. This does not cover every assignment route or mutable slice. |
| Local `var` binding/reassignment | The exclusive-reference root rule does not introduce `Mut` merely because the local is mutable. The earlier blanket local-mutation row was too broad. |
| `.value` on compiler `Knowledge<T>` | The `TyKnowledge` branch in `checker_check_field_access_inplace` requires `Epistemic` and reports **E170** when absent. This is not a claim that every field named `value` triggers E035 or an effect. Ordinary library structs use their own field types. |
| Indexing, casting, printing, division, or observation | Inspect the particular builtin, checked operation, and selected profile. Do not assume one historical operation/effect table is exhaustive or uniformly enforced. |

The [effects specification](../../spec/2026-10/03-effects-handlers-and-concurrency.md)
records named-body propagation, closure inference, and host-mutation boundaries.
The [epistemic specification](../../spec/2026-10/04-knowledge-uncertainty-and-provenance.md)
separates extraction from uncertainty/provenance semantics.
