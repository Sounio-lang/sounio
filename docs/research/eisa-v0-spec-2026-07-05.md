# EISA v0 — Epistemic ISA specification (2026-07-05)

Status: draft v0, operator-approved direction (full-runtime lane model,
spec + expander as first deliverable). Lineage:
`docs/research/eisa-precision-track-2026-07-05.md` (phases 0–3 delivered:
dd64, ErrorDist, witnesses). This document defines the low-level
epistemic syntax itself.

## 1. Thesis

Classical ISAs expose one lane per register: the value. Everything a
numerical scientist actually needs to reason about — how far the stored
value is from the true value (roundoff), and how far the true value is
from the physical quantity (measurement uncertainty) — lives outside the
machine model, in the programmer's head or in offline analysis. EISA
makes both first-class machine state:

| Lane | Meaning | Carrier (v0) | Discipline |
|---|---|---|---|
| `val` | stored value | `f64` | IEEE-754 binary64, round-to-nearest |
| `err` | signed roundoff correction: true ≈ val + err | `Dd64` (hi+lo) | error-free transformations, essentially exact |
| `u` | GUM standard uncertainty σ of the *true* value | `f64` | JCGM 100:2008 first-order propagation |

The separation matters: `err` is *knowable and measured* (EFT residuals
are exact by Dekker/Knuth theorems); `u` is *irreducible and modeled*
(comes from the measurement, propagates in quadrature). An ISA that
conflates them cannot support the gate below.

Operator decision (2026-07-05): **full-runtime** — all three lanes are
carried in the register at runtime, on every operation. Cost is accepted
for maximal auditability; a static-ledger mode may be added later as an
optimisation, never as the default semantics.

## 2. Register model

An epistemic register `eN` is the triple `(val: f64, err: Dd64, u: f64)`.
Reference implementation: `EReg` in `stdlib/eisa/core.sio`.

Reconstruction invariant: `true(e) = val + err.hi + err.lo` (evaluated in
dd64). For `eadd`/`esub` chains the invariant is exact to dd64 precision
(the add residual is exact by TwoSum); for `emul`/`ediv`/`esqrt` it holds
to first order in `err` (the `err × err` cross terms, of magnitude
O(err²), are dropped).

## 3. Textual syntax (`.eisa`)

Line-oriented, one instruction per line, `;` starts a comment that runs
to end of line. Tokens are separated by one or more spaces or tabs;
there is no other whitespace significance. The textual surface is
**versioned and not frozen**: every `.eisa` file must begin with a
`.eisa v0` header line, and the grammar may change until v2 (compiler
integration) validates it end to end (review finding, xai 2026-07-05).

Token definitions (complete — a v1 parser must not need to guess):

```
reg       := "e" digit+                    ; virtual, unbounded in v0
label     := ident ":"                     ; column 0, own line or prefix
ident     := alpha (alpha | digit | "_")*  ; no ":" or digits at start
sym       := ident                         ; storage symbol inside [ ]
fconst    := f64 literal with mandatory "." (e.g. 0.5, 1.0e-3)
int       := digit+
```

Grammar:

```
program   := header line*
header    := ".eisa" "v0"
line      := [label] [instr] [";" comment]
instr     := reg "<-" op
           | "egate" reg ["," "k" "=" int]
           | "estore" "[" sym "]" "<-" reg
op        := "eload" "[" sym "]"
           | "econst" fconst
           | "eadd" reg "," reg
           | "esub" reg "," reg
           | "emul" reg "," reg
           | "ediv" reg "," reg
           | "esqrt" reg
```

`[` and `]` are separate tokens around `sym`. `!err eft` flags from
earlier drafts are dropped in v0: the lane model is full-runtime, so EFT
capture is unconditional; a `model` mode would reintroduce the static
ledger and is deferred. `egate` always gates against the register's own
`u` lane (no `budget =` clause; one budget semantics, no dialect).
`estore` writes **all three lanes**; `eload` reads all three, and a
symbol with no err/u metadata loads as `err = 0, u = 0` — i.e. storage
is epistemic by default, never silently lossy.

Example (`dose_step.eisa`):

```
.eisa v0
dose_step:
  e0 <- eload [ x ]     ; val, err, u all loaded
  e1 <- econst 0.5      ; exact constant: err = 0, u = 0
  e2 <- emul e0, e1     ; residual of the multiply captured exactly
  e3 <- eadd e2, e2
  egate e3              ; ok | marginal | reject -> receipt
  estore [ y ] <- e3
```

### 3.1 Lane invariants (machine rules, not conventions)

Review (xai, 2026-07-05) flagged that without these the full-runtime
model silently produces garbage. They are ISA rules; the reference
implementation and any expander must enforce them:

- **I1 (u non-negative).** `u >= 0` always. `eload`/`econst` with a
  negative `u` is a malformed program: the loader must reject it before
  execution (not clamp — clamping hides data corruption).
- **I2 (NaN/Inf poisoning).** If any lane of any operand is NaN or Inf,
  the result register is *poisoned*: `val = NaN, err = 0, u = Inf`, and
  every `egate` on a poisoned register emits `reject` with
  `poisoned=true` in the receipt. Poison propagates; it is never
  silently cleared. (`u = Inf` is the honest statement: we know nothing.)
- **I3 (err overflow).** If the err lane overflows to Inf while `val`
  is finite, the register is poisoned per I2. EFT exactness theorems
  hold only in the finite range; outside it the reconstruction invariant
  is void and the machine must say so.
- **I4 (econst exactness is an ISA rule).** An expander or optimiser
  that turns `econst c` into anything with `err != 0` or `u != 0` is
  non-conforming — enforced by witness, same discipline as the
  no-reassociation rule in §6.
- **I5 (u == 0 gate with NaN roundoff).** Covered by I2: NaN roundoff
  means the register is poisoned, so the gate is `reject` before the
  `u == 0` special case is reached. The special case only ever sees
  finite lanes.

Enforcement status: v0.1 reference implementation covers the finite-lane
semantics and the gate; the I1–I3 poison/reject witnesses land in v1
together with the parser (they need `eload` of malformed metadata to be
expressible). Until then I1–I5 are normative but only partially
witnessed — recorded here so the gap is auditable, not discovered.

## 4. Instruction semantics

Each instruction is *defined* by its reference function in
`eisa::core`; the expander must be observationally equal to it.

| Instruction | val lane | err lane (EFT-measured) | u lane (GUM first order) |
|---|---|---|---|
| `econst c` | `c` | `0` | `0` |
| `eload [x]` | stored value | stored correction (or 0) | stored σ |
| `eadd x, y` | `fl(x+y)` | `x.err + y.err + TwoSum-residual` (exact) | `sqrt(x.u² + y.u²)` |
| `esub x, y` | `fl(x−y)` | `x.err − y.err + residual` (exact) | `sqrt(x.u² + y.u²)` |
| `emul x, y` | `fl(x·y)` | `x.err·y.val + y.err·x.val + TwoProd-residual` | `sqrt((y.val·x.u)² + (x.val·y.u)²)` |
| `ediv x, y` | `fl(x/y)` | first-order quotient rule + measured residual | `(1/\|y.val\|)·sqrt(x.u² + (q·y.u)²)` |
| `esqrt x` | `fl(√x)` | `x.err/(2√x)` + measured residual | `x.u/(2√x)` |
| `egate x` | — | compares `\|err\|` against `u` | emits receipt (below) |

Independence assumption: quadrature on the `u` lane assumes uncorrelated
inputs (GUM eq. 10 with zero covariances). Correlated propagation is
explicitly out of scope for v0; using EISA on correlated inputs
overstates or understates `u` and the receipt must record the
assumption.

## 5. The gate

`egate` is the point of the whole design: roundoff must be *negligible*
relative to measurement uncertainty, otherwise the computation is
numerically polluting the science.

```
roundoff = |err|  (dd64, collapsed to f64)
budget   = u
reject   if roundoff * 10  >= budget     (roundoff within 10x of u)
marginal if roundoff * 100 >= budget     (within 100x)
ok       otherwise                       (at least 100x below u)
```

Special case `u == 0` (exact input): `ok` iff `roundoff == 0`, else
`reject` — exact claims admit no roundoff.

Rationale for 10x/100x: GUM (JCGM 100:2008 §7.2.6) reports u to at most
2 significant digits; a contamination below 1 % of u (100x) is invisible
at that reporting precision; between 1 % and 10 % it can perturb the
second digit (marginal); above 10 % it is visible (reject). The
thresholds are reporting-driven, not statistical. They are the *default
policy*, recorded in every receipt; a future `k =` clause may widen the
confidence multiplier, but the reject/marginal ratios stay fixed in v0
(one gate semantics — dialects are how ISAs rot).

Receipt (one line per gate, machine-parseable, self-describing):

```
eisa-receipt: v=0 gate=<ok|marginal|reject> roundoff=<f64-hex> u=<f64-hex>
  site=<label>#<n> policy=10/100 cov=assumed-zero poisoned=<0|1>
```

(single line; wrapped here for readability). Fields answering the audit
findings: `v` (receipt schema version), `site=<label>#<n>` where `n` is
the dynamic occurrence count of that gate site (disambiguates loops),
`policy` (the thresholds actually applied), `cov=assumed-zero` (the
independence assumption is *in the receipt*, not just in prose),
`poisoned` (I2). Values are printed as f64 hex bit patterns, not
decimal, so receipts are bit-reproducible. A full provenance chain
(program hash, input snapshot) is v2 material — receipts get embedded
in build artifacts there; v0/v1 receipts are execution evidence, not
tamper-proof audit records, and say so via `v=0`.

## 6. Lowering contract

The expander rewrites each EISA instruction into a fixed sequence of
plain f64 operations over the three lanes (TwoSum: 6 flops; TwoProd
no-FMA: 17 flops; plus dd64 bookkeeping). Two hard rules, inherited from
the dd64 compiler contract:

1. **No reassociation, no FMA contraction** inside expanded EFT
   sequences. The bit-exactness witnesses
   (`tests/stdlib/math/test_dd64_eft_exact.sio`,
   `tests/stdlib/eisa/test_eisa_core.sio` W1) are the enforcement: if an
   optimiser pass breaks them, the pass is wrong.
2. **Observational equality with `eisa::core`**, made testable (review
   finding: the bare claim is unfalsifiable): equality is checked by a
   differential witness harness that runs the same `.eisa` program
   through (a) the reference functions and (b) the expanded sequence,
   and compares `val` bit-exactly (f64 bits), `err` bit-exactly as the
   pair (hi bits, lo bits), and receipts as strings. The distinguishing
   input set is the witness corpus (cancellation, quadrature, poison,
   round-trip cases) — the same corpus that gates dd64. Equality over
   the corpus is the conformance claim; no stronger claim is made.

Cost model (per instruction, v0 full-runtime): `eadd` ≈ 6 + 22 + 3
flops (residual + dd64 err bookkeeping + quadrature with one sqrt);
`emul` ≈ 17 + 30 + 5. Roughly 8–15x the bare op. This is the price of
auditability and it is paid only inside `eisa` regions, never globally.

## 7. Phasing

| Phase | Deliverable | Status |
|---|---|---|
| v0.1 | `stdlib/eisa/core.sio` reference semantics + witnesses | this drop |
| v0.2 | this spec, math-reviewed + design-reviewed (xai; deepseek/gemini keys down) | this drop |
| v1 | `.eisa` textual parser + expander in Sounio, receipts to stdout, differential conformance harness | next |

| v3 | GPU unification: same three-lane semantics over `epi_wmma_mm16` tiles | research |

Ordering note (review finding e): the reviewer argued semantics should
be validated inside the compiler before freezing a textual surface.
Accepted in substance: that is why the grammar is explicitly versioned
and non-frozen until v2, and why v0.1 (reference semantics + witnesses)
lands *before* any parser. The textual form in v1 is a debugging and
witness surface, not a stability commitment.

## 8. Relation to existing work

- `native::error_policy` (`ErrorDist`) is the *static* model: predicted
  error distributions at compile time. EISA `err` is the *measured*
  counterpart at runtime. The pair gives the falsifiable loop: predicted
  vs measured, witness W3 (measured ≤ modeled envelope).
- `math::dd64` supplies the EFTs and the err-lane carrier; EISA adds no
  new numerics, only machine-level structure and receipts.
- GPU `epi_wmma_mm16` already runs dual value+σ tiles; EISA v3 extends
  that to the err lane.

## 9. Out of scope (v0)

- Correlated uncertainties (covariance matrix propagation)
- f128/qd128 carriers for the err lane (dd64 suffices until witnesses fail)
- Control flow in `.eisa` text (straight-line blocks only in v1)
- Any claim of hardware implementation; EISA is a software ISA over
  IEEE-754 hardware
