# EISA v1 — plan (post-E5)

Date: 2026-07-05
Status: draft for review — v0 (E0–E5) is complete and gated; nothing here
changes v0 semantics.
Lineage: extends `eisa-stack-architecture-2026-07-05.md` (E0, as-built
notes through E5). Format words, receipt fields and opcode numbers below
are relative to that document.

v0 shipped a straight-line, 9-opcode, 3-lane machine with a differential
conformance corpus across three executors (reference chains, EVM, x86 AOT
bridge) plus tamper and anti-vacuity lanes. v1 has one scientific goal:
**make real kernels expressible** (PK dose steps, fixed-point iterations,
full Rump 1988) without weakening any of the v0 witnesses.

## 1. Naming — DECIDED: Metron (operator approval, 2026-07-05)

The surface language (the `epistemic fn`/`let`/`gate`/`store` subset the
E3 backend compiles) is named **Metron** (μέτρον, "measure"). Decision
criteria was future adoption: two syllables, identical pronunciation
across English/Portuguese/Greek, weak name collisions, and the pitch
tells itself — *Metron: computation as measurement* — anchoring directly
in the project's metrological identity (GUM uncertainty, EFT-measured
roundoff, receipts, SI units).

Candidates considered and set aside: Martyria (μαρτυρία, semantically
apt but evokes *martyr* in English), Gnomon (unstable pronunciation),
Doxa (phonetic adjacency to *doxxing*), Tekmor (most unique/searchable
but opaque to newcomers).

Public-naming corollary: the executor is **Metron VM (MVM)** in
external-facing text, because the bare "EVM" acronym is saturated by the
Ethereum Virtual Machine and would poison search and conversation.
Internal identifiers do not change in v1 (`eisa::backend`, `eisa::evm`,
`.eisax` stay as-is); the rename surface is documentation only.

## 2. v1 instruction set additions

All new opcodes come from the reserved space 9..15; the v0 validator
rejects them, so v0 images are unaffected and v1 images are rejected by
v0 validators (fail-closed on both sides). Container version word bumps
0 → 1. Instructions stay 4 words (`op`, `dst`, `a`, `b`).

| op | name | semantics |
|---|---|---|
| 9  | `emov dst, a` | register copy: bit-faithful for `val`, `err.hi`, `err.lo` and the poison flag (closes the v0 move-via-eadd zero-sign caveat, arch doc §3.1b: `-0.0` survives, `err` is copied not re-derived). The `u` lane is the explicit carve-out: every u-lane write, including copies, canonicalises `-0.0` to `+0.0` (§7), so I1 stays uniformly executor-checkable. |
| 10 | `ebr t` | unconditional branch to instruction index `t` (word `a`; `dst`, `b` zero). |
| 11 | `ebrz r, t` | branch to `t` iff `val(r) == 0.0` (IEEE, so `-0.0` branches too). |
| 12 | `ebrn r, t` | branch to `t` iff `val(r) < 0.0`. |
| 13 | `ehalt` | stop; same observable end-state as falling off the code end (v0's only stop). |
| 14–15 | reserved | still rejected in v1. |

Design rules for branches:

- **Targets are absolute instruction indices**, validated at load: `0 <=
  t <= n_code` (`t == n_code` means halt). No computed targets — the
  branch-target set is static, so the loader can still enumerate every
  reachable path shape.
- **Branching on a poisoned register is itself poison-relevant**: the
  machine takes the not-taken path (fall-through) AND sets a sticky
  machine flag `br_poisoned`; every subsequent `egate` receipt carries
  `poisoned=1`. Rationale: a control decision made on garbage cannot be
  laundered by later clean arithmetic. This is I6, the first new poison
  invariant since I1–I5.
- **The epistemic branch caveat (the novel part, stated honestly):**
  `ebrz`/`ebrn` decide on the `val` lane alone. When `|val(r)|` is
  smaller than the register's own uncertainty (`u(r)` or `|err.hi(r)|`),
  the branch direction is epistemically unsupported — the E5 kernel is
  exactly a case where `val == 0.0` while the true value is `~2^-80`.
  v1 does not forbid this (that would make the machine unusable); it
  makes it **observable**: a branch whose operand satisfies the single
  symmetric predicate `|val| <= max(u, |err.hi|)` **with the exact case
  excluded** — if `max(u, |err.hi|) == 0` the operand is exact and the
  branch is never frail, whatever `val` is — increments a per-run
  counter `frail_branches`, reported in a new receipt field (§4). The
  v1 policy is count-only — `frail > 0` never forces `poisoned=1`;
  escalation (warn → poison) is deferred until a corpus kernel shows
  which default is right.
- **Validation scope, stated explicitly:** v1 target validation checks
  index range only (`0 <= t <= n_code`). There is no register-window or
  stack discipline to protect yet; if v2 adds calls or callee-save
  state, target validation must grow with it. Indirect branches and
  jump tables stay out (see §10) precisely so the target set remains
  static.

## 3. Termination and determinism (fuel)

Backward branches make non-termination expressible, which threatens the
conformance model (byte-identical stdout requires termination). v1 adds
a **fuel word** to the container header (word 6, after the hash; hashed
like everything else): the maximum number of instruction steps. The
loader rejects `fuel <= 0` or `fuel > 2^24`. Exhausting fuel is a
distinct machine stop: the machine emits one final receipt carrying
`stop=fuel` and `poisoned=1` — that receipt only; there are no
subsequent receipts once the machine has stopped, so no wider poisoning
rule is needed. It is an honest outcome, not an error path. Both the
EVM and the bridge count steps; the bridge decrements a register and
checks per instruction (cost measured, expected ~10 B/instr).

Fuel accounting is defined per **executed instruction**, normatively
(review finding, V1a): a branch consumes one fuel step for itself; if
its taken target is `n_code` (the halt pseudo-target) the machine then
stops with **no further decrement** — the halt edge is free. Falling
off the code end and executing `ehalt` likewise consume the step of
the instruction that ran, nothing more. Both V1b implementations (EVM
and bridge) must follow this rule so step counts — and therefore
`stop=fuel` receipts — cannot diverge on the same image.

Boundary case, pinned (review finding, V1b): when the last executed
instruction both exhausts fuel exactly AND reaches natural termination
(halt pseudo-target, `ehalt`, or code end), the run reports
`stop=run` — the machine halts at that instruction's effect and the
fuel check happens at the next fetch, which never occurs. Fuel
exhaustion (`stop=fuel`) is reported only when fuel reaches zero with
instructions still pending. Deterministic, and both executors must
agree.

I6 note (review finding, V1b): the forced fall-through on a poisoned
branch operand is canonical, not arbitrary — the poisoned `val` is
NaN, and IEEE comparisons on NaN are false, so `ebrz`/`ebrn` fall
through under plain IEEE semantics anyway; I6 adds the sticky flag on
top. Frail boundary: `|val| == band` counts as frail (sound
over-approximation, documented rather than strict).

Determinism claim unchanged: same image ⇒ same receipts, now because
fuel is part of the hashed image.

## 4. Receipt v2

v1 receipts keep every v=1 field byte-compatible and append two fields:

```
eisa-receipt: v=2 prog=<hash> gate=<n> reg=e<r> val=<s,e,m> roundoff=<s,e,m>
              u=<s,e,m> poisoned=<0|1> frail=<count> stop=<run|fuel>
```

`frail` is the `frail_branches` count at gate time; `stop` appears only
on the final receipt if fuel ran out. The v0 subnormal-injectivity
caveat stays (receipts exact for normals + zero); fixing subnormal
decomposition is v2 material unless a v1 kernel hits it.

## 5. Budgets

v0 limits (16 regs, 32 instrs, 16 consts) were sized for straight-line
E5 and are the reason full Rump did not fit. v1: **64 registers, 256
instructions, 64 constants, 32 mem slots**. Validator numbers only; the
encoding already carries them as words. The E3 backend keeps its
register free-list; with 64 regs the full Rump polynomial fits with the
move-synthesis overhead measured on the E5 kernel (18 emitted
instructions for 13 source statements, ~1.4x — recorded here as the
baseline for future budget discussions).

## 6. Surface (backend) growth

Two statements, lowered to the new opcodes, keeping the grammar
line-oriented and shunting-yard-parsable:

```
while <ident> != 0.0 { ... }      -> ebrz/ebr loop shape
if <ident> < 0.0 { ... }          -> ebrn skip shape
```

Deliberately restricted: the condition is a single identifier against
literal zero (no general boolean expressions in v1), and that
identifier must name a register already written earlier in the program
— the backend's symbol table enforces define-before-use in conditions
exactly as it does in expressions. This covers
fixed-point iteration (`while delta != 0.0`) and guard clauses, which is
what the target kernels need; anything richer waits for evidence.

## 7. u-lane -0.0 normalisation

The bridge's sign-bit poison test diverges from the EVM's IEEE `u < 0`
for `u == -0.0` (documented v0 caveat, unreachable in the v0 corpus).
v1 closes it at the semantic level: **every u-lane write normalises
-0.0 to +0.0** (EVM: explicit check; bridge: `maxsd` with +0.0 before
store). The invariant I1 becomes "u is nonnegative and its bit pattern
is never negative zero", checkable on both executors identically.

## 8. Conformance corpus extension

Every new opcode and both branch polarities must appear in at least one
corpus program, plus:

- a loop kernel (fixed-point iteration with a known step count) — same
  receipts EVM/bridge, fuel far from the limit;
- a fuel-exhaustion witness (tight fuel, `stop=fuel` receipt identical
  on both executors);
- a frail-branch witness (the E5 cancellation kernel extended with a
  branch on the collapsed register — `frail=1` expected);
- an `emov -0.0` bit-faithfulness witness (the v0 caveat, now fixed,
  becomes a positive test);
- full Rump 1988 under the new budgets, with the dd64 honest-boundary
  framing from `test_dd64_cancellation.sio` (err lane lands within
  measured bounds; the ~122-bit exact value stays out of reach until a
  qd128 err lane, which remains v2 material).

Tamper and anti-vacuity lanes extend unchanged to the new programs.

## 9. Phasing

| Phase | Deliverable | Gate |
|---|---|---|
| V1a | format: version word 1, fuel word, ops 9–13 encode/validate, budgets | round-trip + reject-v0/v1-cross witnesses |
| V1b | EVM: emov, branches, fuel, I6, frail counter, receipt v2, u -0.0 norm | differential vs extended reference chains |
| V1c | backend: `while`/`if` statements, budget lift | golden compiles + honest rejections |
| V1d | bridge: new templates (jmp/jcc, fuel decrement, maxsd norm) | full corpus byte-identical + tamper + anti-vacuity |
| V1e | showcase: Rump-full + fixed-point loop kernel end-to-end | corpus green on both executors; Rump err-lane bounds byte-identical EVM/bridge (not merely within tolerance) |

Same discipline as E0–E5: each phase is one commit, offload-reviewed
where math-bearing (branch poison semantics, fuel bound argument, Rump
budget arithmetic), witnesses on `lean_single` until
BLK-20260705-madaros-check-hang-strlib closes (fix dispatched).

## 10. Explicitly deferred (v2+)

- qd128 error lane (needed for exact Rump, ~122 bits);
- per-site gate policies in receipts;
- subnormal-injective receipt decomposition;
- general boolean conditions, function calls, memory indexing;
- indirect branches / jump tables (kept out so the branch-target set
  stays static and loader-enumerable);
- integration of the backend into the real compiler driver (stays a
  standalone `stdlib/eisa/` driver while the shared-worktree discipline
  holds);
- growable / chunked source input for the Metron surface compiler. The
  `Str` type it consumes is a fixed 256-byte buffer whose concatenation
  TRUNCATES SILENTLY at capacity (`stdlib/str/lib.sio`); a V1c audit
  witness failed with misleading line-number errors because the test
  builder handed the compiler a source cut mid-line. Interim tripwire
  shipped in V1c: distinct status `-18` when parsing ends structurally
  unclosed AND `src.len >= 256` (a complete source ending exactly at
  byte 256 parses closed and is unaffected). The 256-byte cap bounds
  realistic v1 kernels well below the 256-instruction image budget, so
  lifting it is a prerequisite for any corpus growth beyond E5-scale
  kernels.
