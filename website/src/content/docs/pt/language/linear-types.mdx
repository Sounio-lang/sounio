# Tipos Lineares e Posse (*Ownership*)

O Sounio garante uma gestão rigorosa e segura de recursos através do seu sistema de tipos lineares (*linear types*). Um valor linear tem de ser consumido exatamente uma única vez: não é permitido descartar silenciosamente descritores de ficheiros (*file handles*), ligações a bases de dados ou buffers alocados na GPU. O compilador rejeita imediatamente programas que omitam o consumo de recursos lineares.

## Estruturas Lineares (*Linear Structs*)

Para exigir que uma estrutura seja consumida exatamente uma vez, declare-a utilizando a palavra-chave `linear`:

```sio
linear struct FileHandle {
    fd: i32
}

fn open_file(path: &str) -> FileHandle with IO {
    // Operação do SO; devolve um descritor linear
    FileHandle { fd: sys_open(path) }
}

fn close_file(handle: FileHandle) with IO {
    sys_close(handle.fd)
    // O recurso 'handle' é consumido e destruído aqui
}

fn main() with IO {
    let h = open_file("/tmp/data.txt")
    // Se omitirmos o close_file(h), o compilador rejeitará o programa
    close_file(h)
}
```

Caso remova a instrução `close_file(h)`, o compilador emitirá um erro estático apontando que o recurso linear `h` não foi devidamente consumido.

## Referências Partilhadas vs. Exclusivas

O Sounio diferencia o acesso a dados através de referências partilhadas de leitura (`&T`) e referências exclusivas de escrita (`&!T`). Note que `&!` não é equivalente ao `&mut` do Rust; o símbolo de exclamação `&!` sinaliza que o acesso é garantidamente exclusivo.

```sio
fn read_value(r: &i64) -> i64 {
    *r
}

fn increment(r: &!i64) {
    *r = *r + 1
}

fn main() with IO {
    var x = 10
    println(read_value(&x))   // Empréstimo partilhado (somente leitura)
    increment(&!x)            // Empréstimo exclusivo (escrita)
    println(x)                // Escreve 11
}
```

O verificador de empréstimos do compilador garante estaticamente que nenhuma referência exclusiva coexista com qualquer outro apontador ativo para a mesma região de memória.

## Semântica de Transferência (*Move Semantics*)

Os valores que não implementem a semântica `Copy` são movidos (*moved*) no momento de atribuição ou passagem de parâmetros. Após essa transferência, o vínculo (*binding*) original deixa de ser válido:

```sio
fn consume(h: FileHandle) with IO {
    close_file(h)
}

fn main() with IO {
    let h = open_file("/tmp/data.txt")
    consume(h)
    // O recurso 'h' já não é válido; utilizá-lo daqui em diante gera um erro de compilação
}
```

## Semântica Afim (*Affine*) e Tipos Escalares

Alguns tipos adotam uma semântica afim (*affine*) em vez de puramente linear: a regra dita que devem ser consumidos *no máximo* uma vez, sendo permitido o descarte silencioso. Os tipos escalares primitivos (`i32`, `i64`, `f64`, `bool`) implementam por omissão a característica `Copy` e podem ser clonados livremente. Estruturas que não incluam explicitamente a palavra-chave `linear` seguem a semântica tradicional de *move*, mas dispensam a obrigatoriedade de consumo antes de saírem de escopo.

## Detalhes de Implementação

O subsistema de verificação de posse (*ownership checker*) reside em `self-hosted/check/ownership.sio` e atua imediatamente após a validação do sistema de tipos. Este módulo rastreia ativamente quais os vínculos que foram transferidos, quais os que se encontram sob empréstimo (*borrowed*) e faz cumprir as regras do contrato de linearidade sobre todas as estruturas declaradas como `linear struct`.

## Ressalvas e Limitações

- **Aninhamento:** Recursos lineares embutidos em estruturas tradicionais (não lineares) são rastreados de forma recursiva pelo compilador.
- **Estruturas de Controlo:** O verificador de posse atual encontra-se em fase de otimização para lidar de forma totalmente integrada com fluxos lineares no interior de braços complexos de `match` ou funções anónimas (*closures*). Consulte a nossa página de estado das funcionalidades para aferir a cobertura atual.
- **Interação JIT:** O motor JIT Cranelift apresenta uma limitação conhecida ao processar mutações via referências exclusivas `&!`; em ambientes JIT, dê preferência a padrões funcionais de retorno por valor para mutações que necessitem de visibilidade no chamador.
