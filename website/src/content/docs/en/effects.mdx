Research language; Sounio 3.0 (pre-release).

This page is the effect system for learners: side effects written in the signature. The [effect checker internals and source map](/learn/compiler/effect-system/) is a different page. It names the checker files. It does not answer this query.

## Why effects are in the signature

A function that only computes a result is interchangeable with its result. A function that also prints, writes memory, divides, or aborts is not. An effect annotation is the compiler's copy of that difference. The reader of a signature can see the difference without opening the body, and the checker can reject a call that would smuggle the difference into a caller that did not admit it.

That matters for tests and for scientific code. A pure helper can be called from anywhere and its result depends only on its arguments. An effectful boundary stays at the edge, where the program talks to the console, the file system, or a mutable buffer. The split is a property of the type, so a later edit that adds a print inside a pure helper is a compile error rather than a surprise in a log.

Sounio does not infer effects for a named function by default. Every named function that performs an effect must write `with` and name it. Omit the clause and both compilers report E035, "effect not declared in function signature". Madaros prints that text from `self-hosted/check/check.sio` when `effects_subset` fails. lean_single prints the same sentence from `tc_effect_violation` and `tc_effect_call_violation` in `self-hosted/compiler/lean_single.sio`.

Closures are the exception inside a named function. `checker_check_closure_expr_inplace` sets `in_closure_body`, accumulates effects the body needs, and publishes that set onto the closure's own signature (`self-hosted/check/check.sio`, from the closure checker through the point where `current_effects` is restored). The enclosing named function does not receive those effects for free. After the closure is checked, the outer effect set is restored. Calling the closure later is an ordinary call: the named function must still declare what the closure requires, or the call is E035.

There is an opt-in for named functions. `SOUNIO_EFFECT_INFER=1` turns on `checker_effect_inference_enabled`. While it is on, a missing effect can be added to the set in force and, when the current signature name still matches, written back onto that function. The flag is off by default. The shipped compilers require the declaration. Nothing on this page should be read as "effects propagate automatically."

## Built-in effects

The names you will see most often are IO, Mut, Div and Panic.

IO covers interaction with the world outside the process: printing, reading, and the other operations the standard library marks with that name. A `println` in a function that does not say `with IO` is rejected. The [IO effect](/learn/effects/io/) page is the short tour of that boundary.

Mut is the effect of writing through an exclusive reference. Sounio spells that reference `&!`, and the function that stores through it declares `with Mut`. A pure reader of a shared reference does not.

Div is division and remainder. A function that divides declares `with Div`, because division by zero is a checked effect rather than an invisible arithmetic accident.

Panic is the abort path: assertions, out-of-range indexing, and casts that the compiler treats as able to abort. A function that can panic says so. A function that does not say so is not allowed to call one that does.

Those four are the common ones. They are not the whole set. `self-hosted/check/effects.sio` defines a closed list of 30 built-in effect names, ids 0 through 29. `effect_named_id_max` returns 29. A name outside that list, outside the held-name list, and outside the user-effect registry is refused. Madaros reports E246 for an unknown name (`checker_emit_e246` in `self-hosted/check/check.sio`). The closed list is the contract. Adding a thirty-first built-in name is a compiler change, not a program.

Madaros stores the effects of the function it is checking in `current_effects`, an array of eight ids (`self-hosted/check/check.sio`). A ninth distinct effect does not fit. The collector emits E246 and does not drop the extra name silently. That ceiling is Madaros. lean_single stores effects in the `FN_EFFECTS` bitmask and accepts nine. The eight-slot refusal is not a rule of both engines.

The subset check exists in both. Madaros calls `effects_subset` (`self-hosted/check/effects.sio`): every id the callee requires must occur in the caller's declared array. lean_single calls `bitset_is_subset` (`self-hosted/compiler/lean_single.sio`): the callee's bits must already be set on the caller. Either way, the caller declares a set and the callee's set has to be contained in it. There is no second, hidden set that the compiler invents for a named function.

This is not row polymorphism. `TyEffectVar` and `TyEffectRow` are type tags in `self-hosted/check/types.sio`, and `ty_effect_var` and `ty_effect_row` build them. Nothing calls those constructors. The helpers in `self-hosted/check/effects_row.sio` (`effect_row_contains`, `effect_row_subset`, `check_handler_coverage`) are defined there and are not called from the rest of the tree. Koka's row is a different language. Sounio's live check is a set.

## What the compiler rejects

The smallest witness is a pure function calling an IO function. `greet` declares IO and prints. `pure_caller` has no `with` clause and calls `greet`. The compilers reject `pure_caller`. `main` in the same file returns 0 and does not call `greet`, so the diagnostic is about the pure caller, not about `main`. The file is a compile-fail test. Its harness comment records the pattern `effect not declared in function signature`.

<EffectSystemExamples group="checked" />

Read that file as the compiler reads it. The call is illegal because the callee's effect is not in the caller's signature. Declaring `with IO` on `pure_caller` would make the call legal and would push the obligation one frame up, to whoever calls `pure_caller`. The obligation stops only at a function that both declares the effect and is the root the program actually runs. It does not stop because the compiler guessed.

The same rule is what a test harness wants. A function under test that declares no effects cannot reach a printer, a store, or a panic unless the test declares those effects too. The signature is the list of ways the test is allowed to leave pure computation.

## Declared effects

A name outside the closed list can still be an effect. The program declares it with `effect`, and the name must not be held.

The collector Madaros runs is `checker_collect_item_inplace` in `self-hosted/check/check.sio`. It has an arm for an effect item and calls `checker_collect_effect_def_inplace`. The comment on that arm dates the change to 2026-10-31. Before that arm, the item fell through and the declaration was inert. EFF-021 in `docs/spec/2026-10/03-evidence.tsv` records that skip. It is not a description of the collector that runs now. A registered user effect takes an id at `100` plus its index in the registry, which is a different range from the built-in ids 0-29.

The caller rule is the same rule as for IO. A function that declares the user effect can call another function that declares it. A function that omits it cannot. Both files below are Madaros tests. The first runs and prints `USER_EFFECT_OK 42`. The second is refused with E035, "effect not declared in function signature".

## Handlers

Madaros implements handlers. The founder ruling of 2026-10-31, in `docs/spec/S07_EFFECT_HANDLERS.md` section 7.4, is deep handlers and linear one-shot continuations. The status note in that file, dated 2026-11-01, says those rules are implemented on Madaros. `tests/run-pass/handler_discharge.sio` is a run-pass test: the handled body prints `handler: PASS`. `tests/run-pass/fx4_resume.sio` resumes once. `tests/compile-fail/fx7_double_resume.sio` refuses a second resume. `tests/compile-fail/fx8_missing_clause.sio` refuses a missing clause.

Resume is linear. At most once on every path through a clause. Zero uses are allowed: the suspended computation is torn down, and that is not an error. Twice is a compile error. Multi-shot continuations and shallow handlers are non-goals of that ruling.

The same status note names the limits that fail closed at compile time. Operations and answers are scalar i64 values. A perform stays in the handled body of the same function. A clause does not capture locals. At most 5 perform arguments, at most 12 clauses, nesting depth at most 8. This page does not paste a handler expression. The tests named above are the source.

This section describes Madaros, the default engine. It does not claim the same handler behaviour for lean_single.

## What is checked

| Piece | Status |
| --- | --- |
| `with` on a named function | Required. A missing effect is E035 on both engines. |
| Built-in names | Closed list of 30, ids 0-29. IO, Mut, Div and Panic are the common ones. |
| Eight effects in one signature | Madaros only. The ninth is E246. lean_single uses a bitmask and accepts nine. |
| Subset check at a call | Both engines: `effects_subset`, and `bitset_is_subset`. |
| `effect` declaration | Registered on Madaros, unless the name is held. Ids start at 100. EFF-021 is the old skip. |
| Handlers on Madaros | Deep, linear one-shot, with the limits in the section above. |
| Effect rows | `TyEffectVar` and `TyEffectRow` exist. Nothing calls the constructors. |

The rows a program can rely on are the built-in list, the subset check, a declared effect whose name is not held, and a Madaros handler inside the limits above. Effect rows are unused types. A held name is not a user effect.

## How this compares

The table states only what those projects' own docs say. It is a map of neighbors, not a claim that Sounio implements their features.

| Language | What the official docs say |
| --- | --- |
| Koka | A strongly typed language with effect types and handlers, and a polymorphic type- and effect system ([readme](https://github.com/koka-lang/koka/blob/master/readme.md)). Effect rows on the types page are an angle-bracket list of labels, a bar, and a tail variable, illustrated there as div, exn, and a row variable ([std/core/types](https://koka-lang.github.io/koka/doc/std_core_types.html)). |
| Effekt | Lexical effect handlers, from the language's own history of the 2020 paper ([evolution](https://effekt-lang.org/evolution)). Contextual effect polymorphism: a block argument's effects are handled at the call site ([effect polymorphism](https://effekt-lang.org/docs/concepts/effect-polymorphism)). User-defined handlers can resume ([handlers](https://effekt-lang.org/docs/concepts/effect-handlers)). |
| Flix | "Flix effect handlers use dynamic scope, deep handlers, and support multiple resumptions." Algebraic effects with multiple resumptions are part of the same chapter ([effects and handlers](https://doc.flix.dev/effects-and-handlers.html)). |
| OCaml 5.3 | Handlers were introduced in 5.0. Syntax support for deep handlers was introduced in 5.3. "effect handlers in OCaml do not provide effect safety; the compiler does not statically ensure that all the effects performed by the program are handled." Delimited continuations "must be used linearly"; using one more than once raises `Continuation_already_resumed`. "OCaml does not support multi-shot continuations." ([manual](https://ocaml.org/manual/5.3/effects.html)) |
| Eff | Effects are first-class, and handlers override them. "We discourage the use of Eff in production" ([eff-lang.org](https://www.eff-lang.org/)). |
| Sounio | Built-in effects are a closed list checked in the signature. A declared effect is checked too, unless the name is held. Madaros handlers are deep and one-shot, inside the limits above. |
