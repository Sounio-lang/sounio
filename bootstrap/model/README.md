# Bootstrap model

A semantics of the x86-64 the two seed loaders run on, written in Lean 4 with
no library beyond core, and the evidence that it says what the CPU does.

| `formal/Bootstrap/SeedData.lean` | The seed files as Lean lists, generated by `gen_seed_data.sh`. CI fails if it is stale. |
| `formal/Bootstrap/Seeds.lean` | Short kernel-checked runs of both seeds, valid and refused inputs; built by CI (`lake build Bootstrap`). |

## What the model says

Only the instruction forms the seeds use are decoded; any other byte sequence
leaves the machine stuck. Registers, flags and stack bytes are `Option`: at entry
only `rsp` is defined, and reading anything undefined leaves the machine stuck.
A run that ends in `exit` therefore also shows that the program reads nothing
before writing it, which the seed listings state in their headers. Flags the
architecture leaves undefined (OF after a shift by more than one) are `none`; a
branch on one is stuck. PF and AF are not modelled.

The environment never fails: `read` returns the next byte or end of input,
`write` writes its byte. The seeds' paths for a failed read or a short write are
not covered by the model; the seed gates (`scripts/ci/root_{a,b}_seed_gate.sh`)
cover them on the real kernel.

## The theorems

`seed_proofs.sh` proves, with `decide +kernel` (the kernel alone, no compiled
code), that

    exec F seedA seedAHex = .exit 0 seedA    -- seed-a reproduces itself
    exec F seedA seedBHex = .exit 0 seedB    -- seed-a assembles seed-b
    exec F seedB seedBOct = .exit 0 seedB    -- seed-b reproduces itself
    exec F seedB seedAOct = .exit 0 seedA    -- seed-b assembles seed-a

where `seedA`, `seedB` are the bytes of the committed executables and the
listings are the committed listings. The kernel keeps a cache for the whole of
one declaration, so a single theorem over 120 000 to 150 000 steps does not fit
in memory. `GenProof.lean` therefore splits each run into lemmas of 1000 steps,
`runS im 1000 sᵢ = .inl sᵢ₊₁`, with the states as literals, and assembles them
with `run_chain`. The checkpoints are not trusted: the kernel checks each lemma.

Measured 2026-11-15: about 13 s and 2.6 GB per 1000-step chunk, 123 to 150
chunks per theorem.

## On every listing

`SeedA.lean` and `SeedB.lean` prove, for every input `L` of bytes,

    (∃ F, exec F seedA L = .exit 0 bs) ↔ HexA L none bs
    (∃ F, exec F seedB L = .exit 0 bs) ↔ OctB L bs

and that each seed exits 1 on every listing its grammar does not describe. The
whole-run theorems above are four instances of what these say about all inputs.

The proof is an induction on the input over one iteration of the seed's loop.
At the loop head each seed keeps its state in two or three registers, as its
listing says. The kernel runs one iteration of the model from an abstract head
state that defines only those registers and rsp, for each head state the
decoder reaches (34 for seed-a, 38 for seed-b) and each of the 256 bytes, and
checks that it returns to the head in the state the reference decoder's step
says, having written the byte it says, or exits 1 where the decoder refuses.
`step_mono` carries each iteration from the abstract state to every concrete
state above it: the model is stuck on any read of an undefined value, so a run
that is not stuck read only what the abstract state defines. Measured
2026-11-15 (job 22889): 749 s of kernel time for seed-a, 1139 s for seed-b.

## Why the model can be trusted

The model is only as good as its agreement with the CPU. `x86diff_gate.sh` runs
random cases of every decoded form on the CPU (`x86diff_cpu`, freestanding, no
libc) and on the model, and compares rip, the 16 registers, CF SF ZF OF and the
stack bytes around rsp. `syscall` is the one form it does not cover; the seeds'
system calls are covered by the whole-program runs above and by the seed gates.

The trust that remains: the Lean kernel, the statement of the model, and that
the CPU tested is representative of the ones the seeds run on.
