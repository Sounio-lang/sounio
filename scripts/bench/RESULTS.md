Reproducible via `scripts/bench/run_bench.sh` (Sounio min-of-N process launches, build baseline
subtracted; pandas 3.0.3 / numpy 2.5.1, perf_counter around the op only). All numbers reproduced
directly (not taken from a subagent). col_sum agrees with pandas bit-for-bit (49999950000000.0).

## What changed (all stdlib, no compiler)
- **col_sum: 8 independent accumulators** break the serial add chain -> instruction-level parallelism (1.5x). mean inherits it.
- **filter_count: a raw-pointer scan** (`bf_count_gt`) instead of an accessor loop.
- **filter_materialize: two-pass** -- count survivors first, allocate the output ONCE at exact size, then fill. Kills the old doubling-realloc churn (~15 reallocs copying the growing buffer for 500k survivors).

## Honest read
- **Scale + correctness**: 1M rows, exact results, ~1000x the fixed frame's 1024 cap.
- **Reductions/scans now within ~2.1-2.6x of pandas** (were 2.3-12x). The residual is pure SIMD: pandas runs AVX 4-wide, Sounio a scalar loop. That is the C3 compiler auto-vectorization dispatch (`docs/handoff/c3_simd_autovectorization_codex_dispatch_2026-07-19.md`) -- the stdlib multi-accumulator/raw-scan is the ceiling without SIMD codegen.
- **groupby at parity**: the more algorithm-bound the op, the closer Sounio gets.
- **inner hash-join (4.1x)**: `bf_join_inner` builds an open-addressing table on the right key (reusing the `bf_ghash` Fibonacci mix), probes the left, then gathers the output COLUMN-MAJOR through raw column pointers. It is correct and scale-proven (100k×60k → 60k matches, oracle-exact), but it is the verb furthest from pandas: `pd.merge` is a hand-tuned C hash-join with SIMD gather, while Sounio hashes and gathers scalar (keys/indices boxed through f64). Measured on SHUFFLED keys — the fair general case; on *sorted-unique* keys pandas hits a near-memcpy fast path (~0.9ms) that a general hash-join cannot match by design. Same C3 SIMD path plus an integer-index gather would close most of the gap.
- **cumulative ops — two more pandas wins (cumsum 0.56x, cumcount_by 0.70x)**: `bf_cumsum` is a single sequential accumulate (O(n), no hash) and **beats pandas' `Series.cumsum()`** (5.0ms vs 9.0ms) — a tight scalar running sum outruns pandas' Series machinery + skipna handling. `bf_cumcount_by` / `bf_cumsum_by` do a per-group running count/sum in one pass through the open-addressing table (key → count/sum so far), aligned to input row order. **`cumcount_by` beats pandas' `groupby(k).cumcount()`** (32.5ms vs 46.3ms) — pandas pays for full groupby construction where Sounio needs only one hash pass. `cumsum_by` (36.1ms vs 22.3ms = 1.62x) is the one loss — pandas' `groupby[v].cumsum()` is well-tuned there. So of the four cumulative variants Sounio leads on two, most notably the plain cumsum. These join the full-outer join as the operations where pandas' generality costs it and Sounio's single-pass directness wins outright.
- **shift / diff / pct_change — the pattern's boundary: 1 win, 2 losses, and they map exactly onto the two pending compiler dispatches**: `bf_pct_change` **beats pandas (0.62x, reproduced 6.1ms vs ~9.9ms across 3 trials)** — pandas' `pct_change` internally does shift + divide + fill-handling, overhead a single fused `(x[i]-x[i-1])/x[i-1]` pass avoids. But `bf_shift` (9.9x) and `bf_diff` (5.9x) LOSE, and honestly so: pandas lowers `shift` to a **near-memcpy** (0.56ms — a raw memory move) and `diff` to a **vectorized SIMD subtract** (1.05ms), while Sounio does a scalar per-element `read_f64`/`write_f64` loop. These are the cleanest evidence yet for the two open compiler dispatches — `shift` is memcpy-bound (mem_copy builtin, #1179; the compiler has an internal `emit_memcpy` but no user-facing builtin) and `diff` is SIMD-subtract-bound (C3 auto-vectorization). So the "single-pass wins" rule has a boundary: it holds when the op has real per-element *logic* (accumulate, deque, divide), but a pure memory-move or a pure SIMD-friendly elementwise op is where pandas' C/numpy lowering wins until Sounio's compiler matches it. Shipped for completeness and correctness (oracle-exact), with the honest ratios.
- **expanding — a win, a parity, and a sqrt-bound loss that surfaced a compiler finding**: `bf_expanding_mean` is a running `acc/(i+1)` and **beats pandas 0.44x** (5.9ms vs 13.3ms). `bf_expanding_var` uses **Welford's online algorithm** (numerically stable, no sum-of-squares cancellation) and lands at **parity, ~1.00x** (14.9ms vs 14.9ms, reproduced ×3 at 0.99–1.00 — honestly parity, not a win). `bf_expanding_std` is the same Welford pass plus a per-element `sqrt`, and it **LOSES 13x** (256ms vs 19.7ms) — not because of the algorithm but because **`sqrt` is currently an extern libc call at ~240ns per element** (measured: 30M calls take 7.3s = 244ns/call; an inline Newton-Raphson seeded via the f64 bit-hack ran ~52ns/call, ~5x faster, confirming the extern-call overhead is the cost, not the math). The fix is a compiler one — lower `sqrt` to the hardware `sqrtsd` instruction (~1–4ns) — which would also flip every statistical verb (std, RMS, norm, distance) from sqrt-bound to competitive. `expanding_mean`/`var`/`std` all match pandas exactly (Welford validated to the [999] value). (expanding sum/max/min are already `bf_cumsum`/`bf_cummax`/`bf_cummin`.)
- **rolling_var / rolling_std (~0.83x / ~2.8x) — Welford chosen for exactness**: `bf_rolling_var` uses a **Welford add/remove recurrence** (as the window slides, remove the leaving value and add the entering one, each updating the running mean and M2). This matches pandas *exactly* at every magnitude — including strongly-trending large-value columns (`i*1e6` → window var 1e12 exact) where a naive sliding `S2 − S1²/w` cancels to ~0.1% off, even with a global-mean shift. It costs a bit more per element than the sum-based version (~35ms vs ~22ms) but that's the right trade for a correctness-native frame; it still lands at ~0.83x pandas (win/parity). `bf_rolling_std` = `bf_sqrt` of the rolling var per row, and is **sqrt-bound (~2.8x)** — the per-element `bf_sqrt` (Newton, ~65ns) dominates; the `sqrtsd` compiler fix would bring it to parity, like every other per-element-sqrt verb. Both correct; the gate locks the trending-large var (1e12 exact) and the large-std `bf_sqrt` path (the buggy builtin sqrt would fail it). Numbers measured under a noisy shared host (load ~16), so ratios are approximate; correctness is exact and gate-verified.
- **rolling_median (~0.8x — a surprise win)**: `bf_rolling_median` maintains one **sorted window buffer**, removing the leaving value and inserting the entering value by binary search + shift each step (`O(n·window)`), then reads the median from the middle (linear interpolation for even windows). Pandas' `rolling().median()` uses a skip-list (`O(n·log window)`), yet at typical window sizes Sounio **beats it (~330ms vs ~420ms = ~0.8x)** — the tight scalar shift loop undercuts the skip-list's per-node overhead. It would flip for very large windows (the `O(window)` shift grows). Correct incl. duplicates and even/odd windows (differentially verified byte-for-byte against a naive per-window sort in the gate).
- **cov / corr (0.78x win / ~1.3x) — and a compiler CORRECTNESS bug found + worked around**: `bf_cov` / `bf_corr` use a **two-pass mean-shifted** formulation (mean first, then the mean-shifted products) — numerically stable (deviations are small, so no catastrophic cancellation even for large-magnitude columns or an outlier first element), unlike a single-pass Σxy−ΣxΣy/n. `bf_cov` **beats pandas 0.78x** (6.7ms vs 8.5ms); `bf_corr` is ~1.3x (the extra sums-of-squares pass + the normalising sqrt). **⚠ While validating corr on large-magnitude columns I found that the compiler's builtin `sqrt` is SILENTLY WRONG for arguments > ~1e6** (`sqrt(1e12)`→1279996 not 1e6; `sqrt(2.8e28)`→2.6e22 not 1.7e14) — so `corr` on large-mean data returned 6.29e-9 instead of 1.0, and (worse) the already-shipped `bf_expanding_std` was silently wrong for any variance >1e12. Fixed by a correct in-stdlib **`bf_sqrt`** (bit-hack seed + 6 Newton iterations, self-correcting at every magnitude, verified ≤1 ULP across a sweep to 1e28). `bf_corr` and `bf_expanding_std` now route through it; the P0 correctness bug is dispatched to CODEX-2 (corrected `souc_sqrt_extern_to_sqrtsd` dispatch) to lower `sqrt` to the hardware `sqrtsd`. Bonus: `bf_sqrt` (Newton, ~65ns) is *faster* than the buggy extern (~244ns), so `expanding_std` dropped 13x→6.8x **and** became correct. The gate now includes a large-variance `expanding_std` case (final std 1000000.5) and a large-magnitude `corr=1.0` case — both would fail under the buggy sqrt, locking the regression.
- **quantile / median (~7x / ~2.2x — an honest loss, and a false-win caught)**: `bf_quantile(col, q)` uses an O(n) 3-way (Dutch-flag) quickselect with median-of-3 pivots on a heap copy (the 3-way split keeps duplicate-heavy / constant columns O(n), not O(n²)), then pandas-default linear interpolation; `bf_median = bf_quantile(0.5)`. Both are pandas-exact (5-value interpolation, constant column, and a 1M `median(0..999999) = 499999.5` scale check). But they **LOSE**: pandas' median/quantile go through numpy's **SIMD introselect** (`np.partition`, ~5–16ms) while Sounio's scalar quickselect + interpolation min-scan is ~34–35ms — median **~2.2×**, quantile 0.9 **~7×** (quantile loses more because `np.quantile` partitions to a single position in ~5ms). This is the same scalar-vs-SIMD ceiling as `sort`; a SIMD partition (C3) is what closes it. **Honesty note:** a first reading showed median at 0.28× ("win") — that was an **asymmetric-contention artifact** (the shared host inflated *pandas'* median to 147ms while Sounio happened to measure clean). The real number came from measuring both sides back-to-back under the same instantaneous load, where the ratio held stable (median 1.9–2.4×, quantile 6.1–8.5× across trials). Lesson banked: on a contended host, trust **same-trial interleaved ratios**, never absolute times or cross-trial comparisons.
- **rank (~0.5x on average-method — a win, with an honest caveat)**: `bf_rank(col, method)` supports the four tie-collapsing methods — 0 average (pandas' default), 1 min, 2 max, 3 dense — via a stable argsort (paired key/index mergesort) then one pass scattering each equal-value run's rank back to its rows. All four are validated pandas-exact (the two-way tie at value 10 gives average 1.5, min 1, max 2, dense collapses to 1/2/…), and a 1M scale check confirms the average-rank sum equals `n(n+1)/2` (a permutation-average invariant). The Sounio cost is the ~130–200ms mergesort, shared by all four methods; pandas' `rank(method="average")` on heavily-tied data is ~370ms, so Sounio **wins (~0.5x)**. **Caveat:** the shared host was under heavy, fluctuating load during this session (load average swinging 2.6–29), so the exact ratio is provisional — every reading was a win (0.38–0.53x) but a quiet-machine re-run should pin the number. The ordinal `first` method is intentionally deferred: unlike the others it needs a distinct rank *per element* (`position` cast to f64 in the hot loop), which measured ~6x slower than the run-constant-rank path in the same session — a likely `i64 as f64`-in-loop codegen cost worth its own look before shipping.
- **ewm_mean (0.86x, modest but reproduced)**: `bf_ewm_mean(col, alpha, adjust)` is a single-pass exponentially-weighted recurrence — `adjust=False` is `y = beta*y + alpha*x`; `adjust=True` (pandas' default) runs a weighted-sum/normalizer pair `num = x + beta*num`, `den = 1 + beta*den`, `out = num/den` so the ramp-up is normalized. Both match pandas bit-for-close (validated to the [999] steady state). It beats `Series.ewm().mean()` ~0.86x (12ms vs 14ms), a modest but stable win reproduced ×3 (0.85–0.88x, never crossing 1.0) — this is a real per-element recurrence, so it lands with the other single-pass-logic wins rather than the memcpy/SIMD losses. It's the narrowest of the wins, honestly labeled.
- **rolling window — a clean sweep, all four beat pandas (0.44x–0.79x)**: this is Sounio's strongest category. `bf_rolling_sum`/`bf_rolling_mean` maintain an O(n) running accumulator (add the entering value, subtract the leaving one) and beat `Series.rolling(w).sum()/.mean()` by ~2x (7–8ms vs 16–19ms). `bf_rolling_max`/`bf_rolling_min` use an O(n) **monotonic deque** of indices (front = window extremum, each index pushed/popped at most once) and still win (10–13ms vs 16–17ms) — the deque max/min is differentially verified byte-for-byte against a naive O(n·w) scan in the gate. pandas' `rolling` carries per-window Cython object/validation overhead that a tight single-pass loop avoids. First window-1 rows take a caller `fill` (pass `make_nan()` for pandas NaN). Note: the sliding sum carries the usual f64 online-sum rounding — for exactness use integer-valued data (as the gate does).
- **cummax / cummin — two more clean wins (0.42x / 0.46x)**: same shape as cumsum. `bf_cummax`/`bf_cummin` are a single sequential compare-accumulate and **beat pandas' `Series.cummax()`/`cummin()`** by ~2.4x (4.8ms vs 11.3ms) — pandas' Series cumulative-extremum carries NaN masking a raw scalar loop skips. The grouped `bf_cummax_by`/`bf_cummin_by` (one hash pass, key → running extremum) run ~1.6x pandas, matching `cumsum_by`. So across the eight cumulative variants (sum/count/max/min × ungrouped/grouped), Sounio wins every UNGROUPED one and pandas wins the grouped sum/max/min — a clean split along the single-pass-vs-groupby-construction line.
- **value_counts (3.0x)**: `bf_value_counts` composes the open-addressing hash-count with `bf_sort_by` — one pass tallies each distinct value's count, the distinct `[value, count]` rows are emitted in first-seen order, then stably sorted by count descending (equal counts keep first-seen order, like pandas' default). The 1M count-probes dominate (the `d`-row sort of the distinct set is negligible), so it lands with the other hash verbs at ~3x pandas' `Series.value_counts()` (~9ms khash). `O(n + d log d)`.
- **unique / drop_duplicates (3.3x / 3.0x)**: `bf_unique` (distinct values, first-seen order) and `bf_drop_duplicates` (keep the first row per distinct key) share the open-addressing hash table (bf_ghash, load ≤0.5) from the hash-groupby — one pass, emit/copy on a key's first sighting. Correct and scale-proven (all-distinct 1M edge, first-occurrence verified). This is the widest gap of the hash verbs (groupby was 1.33x) simply because pandas' target op here is *lean*: `Series.unique()` / `drop_duplicates` on a low-cardinality column is a khash factorize that finishes in ~8ms, so Sounio's honest ~25ms one-pass probe is 3x it — same scalar-probe-vs-C-khash gap as elsewhere, just against a cheaper baseline. (Tried an interleaved occ+key table for one-cache-line probes; it was *slower* — with few distinct keys the occupied slots are already cache-resident, so the bigger buffer only added calloc cost. Kept the clean two-buffer layout.)
- **sort_by (2.62x / 2.15x vs stable)**: `bf_sort_by` argsorts a (key, original-row) index list with a bottom-up **stable** mergesort, then gathers each output column column-major through the sorted indices. Two optimizations took it from ~4x to 2.6x: **paired key+index buffers** (compare sequential `key[a] <= key[b]` instead of a random gather `keys[idx[a]]` that cache-thrashes the 8MB key array) and **ping-pong buffers** (no O(n) copy-back on each of the ~20 merge passes). Correct for all non-NaN f64 (direct `<=`), stable (equal keys keep input order — verified).
- **sort_radix — a bounded-key fast path, NOT a universal win (honest read)**: `bf_sort_radix` is an LSD radix sort over the f64 bit-keys (11-bit digits, ≤6 passes) with the IEEE sign-bit order transform, made adaptive by a **diff-mask that skips digit-passes whose bits are uniform across all keys**. It is differentially verified byte-for-byte against the stable mergesort (mixed-sign *and* ties-heavy data), so it is provably correct including tie order. **The headline (continuous doubles) is 2.48x pandas — essentially the same as the mergesort (2.62x)**: on full-entropy data every pass runs, so radix's O(n) buys nothing over the O(n log n) mergesort here, and both are bottlenecked by the same unavoidable random gather (scatter writes + the final column gather by sorted index; numpy's introsort+take is optimized C). Radix's real win is when the KEY COLUMN HAS BOUNDED RANGE OR LOW CARDINALITY — IDs, categories, quantized/binned measurements, timestamps in a window — where byte-skip cuts it to 1-3 passes: **1.50x pandas on a 1e6-range key, 1.37x on 1000 distinct keys, and ~1.8x faster than the mergesort**. So it is a fast path to reach for on bounded keys, and equivalent to `bf_sort_by` otherwise. (Earlier I nearly headlined the 1.4x bounded-integer number as the general result — that was radix's best case, not the measurement-data case; the continuous-double number is the honest one.) A true universal win needs SIMD codegen (C3) for the gather, or a GPU-resident sort.
- **left / full outer join (1.71x / 0.92x)**: `bf_join_left` / `bf_join_outer` share one engine with `bf_join_inner` (build-on-right, probe-left), keeping every left row (unmatched right cells take a caller `fill`, e.g. `make_nan()` for pandas NaN) and, for the full outer, appending right rows whose key no left row matched (left cells filled, join key coalesced). **The full outer join actually BEATS pandas (0.92x)**: `pd.merge(how="outer")` factorizes both sides, unions the keys, and does NaN alignment (~30ms here), while Sounio's outer is just the left pass plus a cheap append of the unmatched right rows (~27ms). The left join (1.71x) is much closer to pandas than the inner (4.1x) because the tighter data (50% match) and the all-left-rows-in-order emit avoid the inner's per-match index churn. Numbers are data-shape dependent (match ratio, key distribution) but reproduced locally on shuffled keys.
- **filter_materialize (3.1x)**: bounded by copying 500k*3 cells one write_f64 at a time; a bulk column-wise copy (memcpy-style contiguous move) would close most of the rest -- a follow-up.
- **GPU**: a single 1M reduction is memory-bandwidth-bound (8MB CPU->GPU transfer > the op); GPU is for GPU-resident multi-op columns (C3b), and the DGX is remote (not benchmarked here).

**Bottom line:** the data layer is scale-correct, algorithmically competitive (groupby parity), and now within ~2-3x of pandas on reductions/scans/filter -- with the remaining gap being SIMD codegen (dispatched) and a bulk-copy filter follow-up.
